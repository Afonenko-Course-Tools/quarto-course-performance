# Визуализация измерений в Perfetto и Speedscope

Perfetto показывает интервалы операций и подтверждённые логические связи. Speedscope открывает уже
записанные V8 CPU-профили. Просмотрщики запускаются отдельно: для рендера не нужны их UI, SDK или
дополнительный runtime.

## От рендера к диаграмме

В каталоге проекта выполните:

```sh
quarto-course-perf render --perf-mode cpu index.qmd
```

Откройте `report.md` в каталоге, напечатанном после запуска. В разделе просмотра выберите
`wall.trace.json` для Perfetto или ссылку на `cpu.cpuprofile` нужного процесса для Speedscope. Файл
открывается через диалог локального просмотрщика; переход по ссылке Markdown сам по себе не
запускает импорт.

`summary` сохраняет интервалы ручных операций, `cpu` дополнительно собирает V8 CPU-профили. Полная
трассировка выбранных функций доступна в изолированном
`quarto-course-perf experiment run --mode trace` с параметрами эксперимента. Режим по умолчанию —
`off`: остаются внешние измерения и отчёт, внутренние трассы и CPU-профили не собираются.

## Где находятся материалы

Обычный `render` сохраняет запуск непосредственно в
`<project-root>/.quarto/course-perf/runs/<run-id>/`. Эксперимент размещает материалы отдельного
запуска в `<workspace>/runs/<run-id>/`. В обоих случаях используйте `report.md` этого запуска: общий
отчёт эксперимента содержит сводные данные.

| Файл                                           | Назначение                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------- |
| `wall.trace.json`                              | Общая wall-шкала исполнителей с калибровкой часов                            |
| `local-wall-001.trace.json` и следующие номера | Отдельная wall-шкала каждого исполнителя без калибровки                      |
| `lua-cpu.trace.json`                           | Локальное процессорное время Lua; исполнители читаются раздельно             |
| `profiles/<process-id>/cpu.cpuprofile`         | Реальный V8 CPU-профиль соответствующего процесса                            |
| `export.json`                                  | Версия экспорта, реально записанные файлы, их шкалы, исходные IDs и качество |
| `run.json`, `summary.json`                     | Результат запуска, качество данных и агрегаты                                |
| `causal.json`                                  | Записанные процессы и связи spans для отдельного анализа                     |

Общий построитель записывает два основных trace-файла при наличии нормализованных диагностических
данных; файл может не содержать интервалов. Локальные wall-файлы появляются только для
соответствующих исполнителей. Ссылки на CPU-профили перечисляют только существующие файлы.
Отсутствие ожидавшегося профиля остаётся ошибкой диагностических данных, даже когда ссылки на него
нет.

Сбор идёт во временном каталоге вне проекта — `staging`. После завершения материалы копируются в
итоговый каталог — `final`. Ссылки отчёта относительные, в том числе при пробелах в пути, и
сохраняются при переносе всего каталога запуска. `run.json.outputDirectory` указывает итоговое
место; `collectionDirectory` и исходные записи подготовки сохраняют место сбора как сведения о
происхождении. Они не являются ссылками для открытия итогового отчёта. Если сохранение не удалось,
сообщение runner указывает оставшийся `staging`.

Очистка `.quarto` удаляет и сохранённую там историю Performance. Для долгого хранения выберите
каталог вне проекта и его публикуемого результата:

```sh
quarto-course-perf render --perf-mode cpu --perf-output ../course-perf-results index.qmd
```

В `--perf-output` задаётся родительский каталог: новый запуск окажется в
`../course-perf-results/<run-id>/`. Относительный путь отсчитывается от текущего рабочего каталога
команды. Параметры `--perf-*` ставятся перед аргументами Quarto. Каталог не должен пересекаться с
`output-dir` или попадать в `project.resources`. Просмотрщики не меняют очистку Quarto.

## Открытие в локальном UI

Для Perfetto распакуйте `perfetto-ui.zip` из
[выпуска v58.2](https://github.com/google/perfetto/releases/tag/v58.2) в отдельный каталог.
Запустите сервер статических файлов для каталога с корневым `index.html`, например:

```sh
python3 -m http.server 8000 --bind 127.0.0.1 --directory /absolute/path/to/perfetto-ui
```

Откройте `http://127.0.0.1:8000/`, нажмите `Open trace file` и выберите trace-файл из итогового
каталога запуска. Разверните процесс и дорожки, выберите интервал: в его свойствах доступны исходные
IDs, статус и качество. Для связанного интервала посмотрите `Following flows`. Открывайте wall,
локальные wall и Lua CPU по отдельности.

Для Speedscope используйте локальную копию версии 1.25.0. Если она получена как пакет `speedscope`,
статический UI находится в `dist/release` внутри пакета:

```sh
python3 -m http.server 8001 --bind 127.0.0.1 --directory /absolute/path/to/speedscope/dist/release
```

Откройте `http://127.0.0.1:8001/` и выберите `cpu.cpuprofile` через диалог импорта либо перетащите
файл в окно. Преобразование в другой формат не требуется. Представление `Left Heavy` помогает
рассмотреть стеки, сгруппированные по затратам. Соответствие профиля процессу проверяется по
`<process-id>` и записи в `processes/`. Профиль содержит выборки CPU, а не точные числа вызовов;
универсального восстановления исходных TypeScript-строк из преобразованных CPU-профилей нет.

Эти серверы обслуживают только файлы UI. Трасса и профиль выбираются браузером локально; для
просмотра не нужно размещать журналы в каталоге сервера или отправлять их во внешний сервис.
Загрузку просмотрщиков выполняйте отдельно от измерений.

## Шкалы, дорожки и стрелки

В исходных событиях и Chrome Trace JSON поля `ts`/`dur` выражены в микросекундах; `displayTimeUnit`
задан как `ms`. В SQL Trace Processor длительность `dur` выражена в наносекундах, поэтому числовые
значения из JSON и SQL отличаются.

`wall.trace.json` объединяет только часы с конечным `time_origin_ms`; значение `0` допустимо.
Неопределённость калибровки сохраняется в `uncertainty_us` и не ограничивает возможный системный
дрейф между процессами. При отсутствии калибровки исполнитель получает отдельный
`local-wall-NNN.trace.json`, без исходного ID в имени файла.
`clock_alignment: "local-executor-only"` означает, что время сопоставимо только внутри этого
исполнителя. Lua CPU также остаётся локальным: положение двух Lua исполнителей в одном файле не
доказывает одновременность их работы. Lua CPU нельзя совмещать с TS wall или складывать с ним.

Числовые `pid` и `tid` — детерминированные IDs представления, а не номера процессов и потоков ОС.
Названия явно содержат «логическая дорожка». Перекрывающиеся операции без подтверждённого
родительства, включая async siblings, получают разные дорожки. Вложенность допустима при записанной
родительской связи; совпавшие границы интервалов сами по себе её не создают.

Исходные `process_id`, `executor_id`, `span_id`, `parent_span_id`, `document_id`, `symbol_id`,
`origin` и `status` сохраняются в metadata/`args`. Исходные атрибуты начала и конца лежат отдельно в
`source_attributes` и `source_end_attributes`, поэтому не подменяют служебные признаки качества
экспортёра.

Стрелка с `relationship: "logical-parent"` соединяет записанные начала двух подтверждённых spans
одного запуска в сопоставимой общей wall-шкале. Она допустима и тогда, когда родитель уже завершился
до начала ребёнка. Стрелка показывает логическое родительство: её длина не является измеренной
задержкой передачи управления или временем запуска дочернего процесса. Время ради стрелки не
сдвигается. Неизвестный родитель, обратный временной порядок, цикл или разные шкалы не дают такую
стрелку. Один `parent_process_id` в записи процесса сохраняется как metadata и сам по себе не
создаёт временной связи.

## Качество и агрегаты

Перед выводами проверьте отдельно результат Quarto, `dataValid` и `quality.coverageComplete` в
`run.json`. Код Quarto `0` не означает полного наблюдения за кодом. `dataValid: true` совместимо с
`coverageComplete: false`: записанные данные пригодны для анализа в пределах наблюдаемого охвата. В
trace и `export.json` соответствующие поля называются `data_valid` и `coverage_complete`; причины
потерь и неполноты сохраняются в `quality`.

Владелец из записанного `attributes.extension_id` получает `extension_attribution: "recorded"`. Если
он восстановлен по префиксу операции, стоит `"derived"`; если оснований нет — `"unavailable"` и
`extension_id: null`. Отсутствующий `document_id` остаётся `null`. Экспортёр не угадывает документ
или владельца по соседнему интервалу.

Повреждённая пара begin/end, дубликаты, несовпадение идентичности, отрицательная длительность или
один незавершённый begin не превращаются в обычный завершённый интервал `X`. Первичные записи и
причины ошибки остаются доступными; пригодная пара со статусом `aborted` сохраняет этот статус. Не
считайте отсутствие интервала доказательством отсутствия операции. Сумма включающих длительностей
тоже не равна времени сборки: интервалы могут вкладываться и перекрываться, отдельное время async
операции без дочерних затрат не вычисляется (`self_time: "not-available"`).

Счётчики без времени не создают событий `C` и временных графиков. `summary.json.counters` различает
приращения из событий (`source: "event"`, `semantics: "delta"`) и итоги исполнителя
(`source: "executor-summary"`, `semantics: "total"`). Не складывайте их как независимые наблюдения
одного счётчика. Пиковая память находится в `run.json.outcome.peakRssKiB`, внешние CPU/wall — там же
в `outcome`. Это агрегаты запуска; периодических выборок CPU/памяти экспорт не добавляет.

`run.json` и `summary.json` отдельного запуска имеют `schema_version: 2`. Производный `export.json`
имеет `schema_version: 1`, `format: "chrome-trace-event-json"`, `run_id`, список файлов с их
шкалами, исходные IDs исполнителей и признаки качества. Он не заменяет первичные JSON/JSONL: сырые
события и сводки исполнителей остаются в формате v1.
