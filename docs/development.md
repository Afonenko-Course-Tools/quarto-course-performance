# Разработка и проверка Performance

Исходный checkout нужен для изменения инструмента, проверки форматов и подготовки выпуска
приложения. Для измерения курса установите команду из
[quarto-course-perf-arch](https://github.com/Afonenko-Course-Tools/quarto-course-perf-arch):
`git clone` → `cd` → `makepkg -si`, как описано в [README](../README.md).

## Подготовка зависимостей

Runtime использует системный TypeScript Compiler API. На Arch установите пакет `typescript`; путь и
переназначение `COURSE_PERF_TYPESCRIPT` описаны в
[README](../README.md#системный-typescript-в-рабочей-копии). Проверка AST и запуск установленного
приложения выполняются отдельно от `tsc --version`.

Собственный `deno.json` включает публичную feature `detect-cjs`: системный Ubuntu `node-typescript`
5.2.2 поставляет legacy CommonJS без `package.json.type`, и Deno 2.7.14 без этого режима возвращает
пустой namespace даже через `createRequire`. Режим
[документирован Deno](https://docs.deno.com/runtime/reference/cli/unstable_flags/#--unstable-detect-cjs)
и присутствует в `deno run --help=unstable`; он наследуется установленным CLI и копией runtime через
их собственный абсолютный config. Реальные AST-проверки подтверждены на файлах официального
Ubuntu-пакета и Deno 2.7.14. Подмена Compiler API, точная версия системного компилятора и
дополнительный module loader не нужны.

Arch `check()` запускает существующие AST-тесты с `--no-check`: это проверка действительного
системного Compiler API и поведения преобразованного кода в чистом исходном архиве. Dev-типы
`@types/node` и npm-зависимости разработки для неё не нужны. Полная статическая проверка остаётся в
обычном `deno task check` и source CI; `--no-check` не переносится в эти gates.

Для typed ESLint и dependency checks установите зависимости разработки обычным `npm ci`. Они не
включаются в runtime-пакет. Системная версия Compiler API не закрепляется точной npm-версией. Для
offline-проверок заранее подготовьте зависимости разработки и необходимые Deno caches; installed
runtime проверяется отдельно с пустым кэшем и `--cached-only`.

Следующие датированные разделы описывают собственные исходные срезы. Их старые npm-архивы и digest
receipts не являются текущим договором. Новый договор и границы проверки — в
[замыкании PR8](releases/2026-11-11-pr8-closure.md).

## Команды проверки

Из корня подготовленного checkout:

```sh
deno task check
deno task test
deno task check:perfetto --trace-processor /absolute/path/to/trace_processor_shell
```

`check:types` включает все собственные TypeScript-файлы `src`, `bridge`, `tools` и `tests`, включая
отдельные preload/subprocess entrypoints, инструменты и fixtures. Включены `strict`,
`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitReturns`,
`noFallthroughCasesInSwitch`, `noImplicitOverride` и `useUnknownInCatchVariables`. `check` также
проверяет запрет явного `any` и подавляющих TS-комментариев, форматирование этого состава, строгий
LuaLS, Pyright и shellcheck. Для `check` нужны LuaLS 3.19.2, Pyright 1.1.414 и shellcheck; CI
готовит их до запуска. [Общий Lua checker](lua-checker.md) использует реальные типы выбранного
Quarto и отдельный отрицательный контроль. `check:lua`, `check:python` и `check:shell` позволяют
проверять соответствующую часть отдельно. Собственная Lua-проверка явно подключает
`typecheck/native.lua` как декларативное дополнение пробелов типов выбранного Quarto; это не
исполняемый Lua-файл. Внешние владельцы передают собственные каталоги типов в общий checker,
декларации Performance им автоматически не подключаются. `test` включает небольшие native fixtures,
поэтому нужны доступные Deno/Quarto/Pandoc и зависимости соответствующих действий. `check:perfetto`
импортирует контрольные трассы настоящим Trace Processor и проверяет интервалы, дорожки,
идентичность и точные концы связей. Версии и контрольные суммы Perfetto приведены в
[инструкции визуализации](visualization.md).

Нативные тесты используют выбранный исполняемый файл Quarto и доступную среду запуска; жёсткий путь
одной локальной установки не является требованием CI. Кэш тестового процесса должен находиться вне
Git-исходника тестового проекта, чтобы подготовка Deno не меняла проверяемое состояние входных
файлов.

[`tests/runtime.ts`](../tests/runtime.ts) разрешает `QUARTO` либо `quarto` через действующий `PATH`
в абсолютный путь до искусственного ограничения `PATH` тестом. Проверки storage CLI используют
внешний временный `XDG_CACHE_HOME`, а `DENO_DIR` берут из фактического `deno info --json` внешнего
процесса. Эти настройки не требуют системной символической ссылки и не исключают кэш из проверки
пользовательских Git-изменений.

Проверка установленного дерева описана в
[Arch-инструкции](arch-package.md#проверка-пакета-до-установки). Она использует
`tools/check-installed.ts --root /absolute/path/to/usr/lib/quarto-course-perf`, чужой `deno.json`,
новый кэш, настоящий summary и отдельный TS trace. Checker сам не создаёт сетевую изоляцию: полный
запрет сети обеспечивает внешняя среда проверки.

Полная интеграционная проверка использует заранее подготовленный чистый Java checkout со всеми
установленными пакетами. Выбор Git checkout и `quarto add` выполняются до проверки. Команда из корня
Performance:

```sh
deno task check:java \
  --project /absolute/path/to/Java \
  --output /absolute/path/to/new-evidence
```

Оба аргумента обязательны и принимают абсолютные пути. Проверка не заменяет пакеты.

`--output` должен обозначать новый каталог вне исходного Java, с уже существующим родительским
каталогом. Перед созданием evidence и запуском Quarto предварительная проверка разрешает пути через
файловую систему . Равенство output исходнику и вложенность в него отклоняются также при завершающем
`/`, `..` и symlink-алиасах; путь будущего output проверяется через его реальный parent.
Предварительная проверка не запускает внешних команд.

Затем команда создаёт изолированные копии, записывает источники, toolchain, команды, коды и прямые
сравнения результатов; выбранный курс не обновляется. Матрица этой приёмки относится к минимальному
Java `4a427b7207cb0ea7138034087100c372bec410ab`: root, `tasks`, `slides`, семь полных пакетов, 14
размещений и 615 файлов пакетов. Эти семь пакетов принадлежат пяти репозиториям: Core, Publisher,
QRC, PrairieLearn и Download. Print, Moodle и Cloud в этом минимальном курсе отсутствуют; их
отдельные owner-проверки не расширяют охват Java. Полный кандидат `4036d3a` сохранён отдельно.
Восемь владельцев реестра не означают исполнения Cloud VM: она в этой матрице не проверяется.

При сопоставлении native/off/summary/cpu значимое учебное содержимое и архивы сравниваются строго.
Фактически динамические native-файлы перечисляются явно. Общая нормализация HTML не служит
доказательством равенства. Точные результаты и исходный SHA проверки записываются отдельно; название
команды не означает, что она уже прошла на произвольном HEAD.

Workflow [`.github/workflows/check.yml`](../.github/workflows/check.yml) закрепляет Quarto `1.11.6`,
Deno `2.7.14`, Hyperfine `2.0.0` и Perfetto `v58.2`. Локальная основная среда использует системный
Quarto `1.11.6` с его Deno `2.7.14`; Arch-пакет отдельно проверяется с системным Deno `2.9.8`. Эти
сведения о средах не заменяют результаты CI и проверки конкретного source SHA.

Самостоятельные фасады ABI 1 — [`bridge/bridge.ts`](../bridge/bridge.ts) и
[`bridge/bridge.lua`](../bridge/bridge.lua). Пакеты явно vendor нужный файл в `observability/`: при
осознанном обновлении ABI скопируйте файл обычной командой из выбранного checkout Performance и
закоммитьте его вместе с проверками поведения пакета:

```sh
install -Dm644 /absolute/performance/bridge/bridge.ts /absolute/owner/_extensions/PACKAGE/observability/bridge.ts
```

Для Lua используйте `bridge.lua`. Print и Moodle используют TS; Cloud — Lua; Core, Presentation,
Navigation, PL, Site, QRC и Download используют оба. Theme не использует bridge. Выбор версии
сохраняется стандартной историей Git владельца. Байтовое равенство с текущим checkout Performance не
является условием совместимости ABI. Проверяйте фактический off-path и диагностические события через
public API. Shipped пакет содержит собственный файл и работает без dev checkout Performance.
`tools/check-owners.ts` проверяет operation registry и удалённый legacy protocol; он не
синхронизирует исходники и не разрешает версии зависимостей.

Однократная миграция исходной разметки завершена; её генератор удалён из поддерживаемого состава.
Новые операции добавляются у соответствующего владельца вместе с его проверками поведения;
постоянные пакеты содержат фасады и ручную разметку. Общий runtime курса ради наблюдаемости не
вводится.

Существование 230 записей не означает покрытия 230 операций конкретным запуском. Для утверждения об
исполнении нужны реальные события, процессы, контекст и quality этого запуска. Учебная модель, Body
и контракт конкретного экспорта остаются у владельцев; Performance описывает измерения. Инвентарь
выбранного проекта и наблюдения пакетов отделены от реестра и состояния агентов TS/Lua. Исторический
первоначальный аудит, где Print/Moodle/Cloud ещё не имели этой разметки, описывает свои исходные
версии; текущие восемь выпусков владельцев и реестр не делают любой установленный старый пакет
автоматически размеченным.

## Подготовка выпуска

Performance владеет исходниками приложения, шаблоном `packaging/arch/PKGBUILD` и оболочкой
`packaging/arch/quarto-course-perf`. Репозиторий `quarto-course-perf-arch` содержит готовый рецепт и
`.SRCINFO`. Версия 2.2.0 использует стандартный GitHub tag archive без собственного генератора,
специального source asset, source receipt или дополнительного commit marker.

После проверки окончательного коммита опубликуйте тег приложения. В репозитории упаковки обновите
`pkgver`, заполните стандартные `sha256sums` через `updpkgsums`, выполните
`makepkg --printsrcinfo > .SRCINFO`, `makepkg --verifysource` и обычную сборку. При изменении только
упаковки того же приложения повышается `pkgrel`.

Проверяйте собранный runtime через `tools/check-installed.ts`: чужой config, пустой кэш, настоящие
summary render и TS trace. Проверка распакованного дерева и установка через pacman в изолированной
Arch — отдельные проверки. Историческая приёмка 2.1.1 и прежние releases сохраняются; они не
доказывают проверку нового выпуска.
