# Интеграция PR8 и техническое замыкание Performance

Точный head PR8 — `86f762e317b237320657a3319c70701d03c72a2e`, исходная ветка
`codex/performance-files-20261105`. Проверен в отдельном временном клоне; ветка не изменялась.
Принятый вход — `3c2d13f`.

Перенесена действительная дельта удаления digest `7a16459 → 86f762e`, включая производителей,
читателей, проверки и подготовку Arch-архива. Полный merge старого PR6-base давал конфликты с уже
принятым кодом. Его архивные стадии `9ba1fd8`/`7a16459` с другим `ProcessObservation`/`completion`
договором не заменяют принятые `outcome`, supervisor, bootstrap-ошибки и отмену процессов. Старый
completion читается только явным импортом завершённого архива.

Новая версия исходников — 2.1.0. Единственный runtime-владелец версии — `deno.json`: существующий
assets helper читает его для CLI и новых run reports. `VERSION` и `PKGBUILD.pkgver`
синхронизированы; исторические записи не меняются.

Сохранены системный Compiler API, его переназначаемый путь, настоящая проверка CPU capability,
физические границы Pandoc data-dir и копирование runtime assets. QRC-нормализация по-прежнему
берётся из выбранного Git blob владельца; собственный hash receipt удалён. Сравнения HTML/ZIP и
native outcomes сохраняются. Старые архивы не переписываются и не становятся доказательством
свежести.

Нормализация разделена на чтение журналов, согласование ожиданий исполнителей, проверку
событий/родительства/счётчиков и итоговый coverage. Config parsing отделён от семантических
ограничений. Исторический импорт сначала проверяет весь план, затем создаёт output. У отчётов
отдельны допуск artifact paths и размещение executor traces; storage отдельно проверяет попадание
диагностик в resources. Experiment использует уже принятый supervisor: при bootstrap failure native
outcome не выдумывается, при отмене сохраняется настоящий результат и завершается только собственное
дерево. CLI повторяет внешний сигнал после сохранения отчёта.

Локальная приёмка 11 ноября:

После независимой рецензии устранены два отказа: неуспешный Hyperfine wrapper не может сделать
сохранённый export успешным измерением; custom Pandoc data-dir выдаёт тот же PreparedScript, который
принимает потребитель отчёта. Непригодное измерение с известным native zero больше не допускается в
benchmark.

Полный structural scope `src/` и `bridge/` проходит budgets 30/5/5; типы и отсутствие dependency
violations проверяются обычным `npm run check-quality`.

- Настоящие Compiler API AST-преобразования и installed-tree CLI с чужим config, пустым cache и
  offline TS trace проходят. Это проверка распакованного приложения, а не заявление о публикации
  нового pacman-пакета.
- Снято 12 реальных native запусков: принятый/итоговый состав, `off`/`summary`/`cpu`, свежий
  проект/повтор. Все VALID, 21 файл результата совпадает побайтно; сохранены wall/CPU/RSS и четыре
  настоящих CPU profiles.
- Дополнительная нативная pre-render стадия читает два QMD, считает слова и формирует включённый
  Markdown. Шесть fresh/repeat запусков сохраняют одинаковый HTML; summary/CPU наблюдают
  действительную операцию, счётчик и атрибуцию владельца. CPU содержит два настоящих профиля на
  запуск.

Fresh означает новый проект/output, repeat — повтор тех же native inputs. Кэши ОС не очищались, XDG
cache изолирован. Во время замера владелец Java выполнял отдельный warm diagnostic. Эти наблюдения
подтверждают смысл метрик и равенство результатов; ускорение из них не заявляется. Локальные raw
receipts, команды и отрицательные результаты сохранены в `/tmp/close-performance`.

Отдельный репозиторий `quarto-course-perf-arch` подготовлен локально. Его действующий рецепт
относится к прежнему опубликованному 2.0.0. Перенос конкретного нового рецепта, `.SRCINFO`,
pacman-приёмка и hosted CI требуют опубликованного исходного коммита, версии и проверенной
контрольной суммы архива. Старый Release не заменяется.
