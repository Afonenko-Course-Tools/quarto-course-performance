## Архитектурные решения плана

Это конкретизация обсуждения, а не утверждение о уже написанном коде.

- Отдельный проект с предлагаемым именем `quarto-course-performance`. Перед созданием проверить наличие подходящего owner; имя/visibility не используются как основание для внешнего действия без задачи реализации.
- Один протокол ABI 1 и два небольших фасада TS/Lua из канонических templates. Пакеты расширений самодостаточны в off.
- Агент устанавливает внутренний diagnostic launcher до загрузки фасадов. Фасад не скачивает агент.
- Самостоятельные clocks и exports TS wall/Lua CPU, при общей идентификации эксперимента/процессов. Причинная связь не означает совпадение часов.
- Строгий запрос function trace проверяет coverage до запуска; частичный trace маркируется partial и не выдаётся за полный.
- Три состояния upstream/clean-control/candidate; legacy cleanup не маскирует off overhead новой разметки.
- Рабочая цель off overhead — 1% с явным INCONCLUSIVE при шуме. Порог, число повторений и вычисление interval заданы в [07](07-validation.md).
- Fresh source default branch tips фиксируются на эксперимент. Если пользовательская актуальная Java ещё только в PR, при реализации нужен explicit remote ref, а не выбор ветки по дате.
- Внутренняя инфраструктура файловая; постоянно работающий collector, базы данных и сервер viewer не обязательны.
- Пилот включает Lua exact trace на штатном Pandoc и TS CPU/target trace. Специальный Lua sampler — отдельный backend, который не обязателен для работоспособности остальных режимов.

## Снятые противоречия

1. **«Новейшее» против воспроизводимости:** актуальность определяется при source discovery, затем входы фиксируются на эксперимент. Новый discovery даёт новый baseline.
2. **Нет внутренних зависимостей в пакете против библиотеки в расширении:** распространяется только маленький стабильный фасад, диагностические зависимости живут отдельно.
3. **Малая стоимость ordinary build против полной trace:** точная trace включается явно в отдельном запуске; ordinary build не выполняет её код.
4. **Ручная разметка против полного function coverage:** она описывает этапы; автоматический слой исследует выбранные поддерживаемые функции с явным coverage.
5. **Единая шкала против разных clocks:** пользователь решил анализировать Lua и TS раздельно на первом этапе.
6. **Новая архитектура против прежних AGENTS/исторических планов:** текущая задача разрешает замену внутренней телеметрии. Старые задания на Releases, публикацию и очистку веток не являются целями Performance.

## Вопросы, которые могут возникнуть только при реализации

- Default branch Java ещё не содержит ожидаемой ревизии — согласовать remote ref.
- Fresh owner contracts несовместимы с fresh Java — предъявить конкретную несовместимость и обсудить необходимую функциональную миграцию; не мерить сломанный baseline.
- Полный запрошенный scope содержит конструкцию, не поддержанную transformer — расширить проверенную поддержку либо согласовать честный ограниченный scope.
- Overhead критерий остаётся INCONCLUSIVE или FAIL — сохранить данные и обсудить исправление/дальнейшие измерения.

Это условные ситуации, не обнаруженные сейчас блокирующие противоречия. Нерешённого вопроса о часах Lua больше нет. Рутинные внутренние решения исполнитель принимает самостоятельно в рамках этих контрактов.
