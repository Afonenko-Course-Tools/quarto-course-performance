# Требования к Performance

См. [архитектуру](02-architecture.md), [контракты](03-contracts.md), [план](05-implementation-plan.md) и [рецензию](08-consistency-review.md).

## Назначение

Выявлять слабые места расширений Quarto на реальных материалах курсов. Система должна показывать реальную скорость сборки, последовательность значимых операций, вложенность вызовов, повторную работу и инициированные расширениями обходы AST. Пилот — актуальная Java из GitHub; затем архитектура должна позволять добавить другие курсы описанием сценариев.

## Обязательные требования

| ID | Требование |
| --- | --- |
| R-01 | Источник исходников — GitHub на момент начала реализации. Получить актуальный tip удалённой ветки по политике [04](04-sources-and-java-pilot.md), записать ревизии и не обновлять их внутри эксперимента. |
| R-02 | Исходники курсов и расширений разрабатывать/измерять в изолированных checkout и рабочих копиях. Сохранить существующие пользовательские каталоги, ветки и изменения. |
| R-03 | Охватить реальную сборку: pre/post-render, Lua-фильтры и shortcodes, вложенные Quarto-процессы, каталог, копирование и архивы, если они вызываются сценарием. Экспорты, не входящие в render, измерять отдельными явными сценариями. |
| R-04 | В обычном режиме не загружать диагностические агенты, преобразователь, профилировщики или внутренние зависимости; не устанавливать hooks и не создавать журналы. Фабрика обрамления возвращает исходную функцию. |
| R-05 | Распространяемые расширения самодостаточны: содержат небольшой локальный интерфейс метрик, но не зависят от наличия внутреннего проекта, сети, npm-сервиса или отдельного расширения Performance. |
| R-06 | Сохранять семантику обычной сборки: значения, ошибки, выводы, настройки, порядок обработки и артефакты. Разрешено менять внутренние API и удалить старые механизмы телеметрии. |
| R-07 | Постоянно размечать значимые операции, инфраструктурные границы и инициированные расширениями обходы AST. Не вставлять ручные таймеры в тела каждой функции. |
| R-08 | Подробная трассировка строит точную карту наблюдаемых вызовов в объявленной поддерживаемой области. Карта всего курса связывает процессы и этапы; она не выдаётся за полную трассировку внутренних функций Pandoc/Haskell, V8 или всех сторонних библиотек. |
| R-09 | Различать вызов API обхода, запуск фильтра, вызов обработчика и посещение узла. Полный документ, фрагмент и поддерево считать раздельно. Не добавлять измерительные обходы дерева ради подсчёта его размера. |
| R-10 | Сохранять вложенность при рекурсии, асинхронных ветвях, корутинах и дочерних процессах. Отсутствующую связь обозначать явно; не восстанавливать родителя по догадке. |
| R-11 | Разделять wall-clock, CPU-время и выборочные оценки. Сохранять clock domain и точность. В первом этапе TypeScript и Lua анализируются раздельно; их временные шкалы не совмещаются. |
| R-12 | Benchmark выполняется на обычных исполняемых файлах и с выключенной телеметрией. Подробные профили объясняют причины и не подменяют результаты benchmark. |
| R-13 | Хранить сырые данные, манифест входов, отчёт о покрытии и качестве, сводку и временные/причинные представления. Разные запуски объединять experiment_id, не превращая их в один вымышленный запуск. |
| R-14 | Потерянные события, ошибки агента, повреждённые журналы и аварийное завершение явно влияют на валидность данных. Не сообщать точные счётчики на основании неполной трассы. |
| R-15 | Совместно подготовить проект профилирования и PR к реально изменённым владельцам расширений. Проверить обычный режим и диагностические режимы на Java перед финальной передачей. |
| R-16 | Проверить стоимость выключенной разметки отдельно от других рефакторингов. Цель — накладные расходы не более 1% в контрольном сравнении; метод и вывод при шуме определены в [07](07-validation.md). Это критерий будущей проверки, не обещание результата. |
| R-17 | Все новые README, пояснения, отчёты и описания PR — на русском. Идентификаторы, команды, форматы и имена файлов сохранять буквально. |
| R-18 | Пилот работает локально на Linux x86-64 после получения исходников из GitHub. Скачивание, сборка инструментов и подготовка данных выполняются вне измеряемого интервала. |

## Режимы

Нормативные значения `mode`: `off`, `summary`, `cpu`, `trace`.

- `off`: обычное исполнение; внешнее измерение разрешено. Benchmark — операция runner, а не дополнительный режим SDK.
- `summary`: значимые размеченные этапы, точные счётчики зарегистрированных операций и инициированных расширениями обходов. Запись обработчиков каждого узла по умолчанию выключена.
- `cpu`: обзорные события плюс выбранный CPU-профилировщик; точные счётчики берутся только из разметки, а не из samples.
- `trace`: обзор плюс точные события поддерживаемых функций выбранных модулей, при явном запросе всей поддерживаемой области собственного кода.

Поддерживаемая область определяется манифестом, а не лозунгом «все функции». В пилоте обязательны точные вызовы обычных и async-функций выбранного TS-модуля и Lua-функций выбранного модуля. Пропущенные конструкции и неинструментированные файлы видны в отчёте; native внутренности остаются вне обязательного охвата.

## Готовность пилота

1. Получены актуальные исходники из GitHub; версия каждой установленной копии расширения прослеживается до owner SHA и package hash.
2. На свежей Java проходят полные обычные сборки `student` и `full`; проверены пять под проектов либо их актуальные преемники.
3. Работают summary, TS CPU-профиль, Lua call/return trace и целевая автоматическая TS-трассировка. Выборочный Lua-профиль со специальным Pandoc описан отдельно; его отсутствие не скрывается и не блокирует эти возможности.
4. В режиме off нет внутренних загрузок, hooks, таймеров телеметрии и файлов метрик; стоимость фасада измерена по [07](07-validation.md).
5. В синтетических fixtures подтверждены вложенные обходы, асинхронное ветвление, корутины, ошибки, завершение процессов и отчёт о потере данных.
6. Обычная и инструментированная сборки дают одинаковые значимые результаты, с документированными узкими нормализациями недетерминированных полей.
7. Для найденного узкого места получен отчёт с доказательствами. Исправление бизнес-алгоритма не является условием успеха системы измерения; выдумывать ускорение не требуется.
8. Подготовлены проверяемые PR и итоговый отчёт с действительными ограничениями. Merge, новые Releases, публикация курса и чистка пользовательских веток не входят в этот этап.

## За пределами пилота

Другие курсы, облачные/удалённые исполнители, регулярный CI-мониторинг, уведомления о версиях, автоматический merge, миграция учебных материалов, распределённая база телеметрии и универсальная инструментализация любого TS/Lua-кода. Пилот не должен требовать специальный Pandoc в обычной сборке.
