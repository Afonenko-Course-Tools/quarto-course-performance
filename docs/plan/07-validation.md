# Проверка реализации и измерений

Связанные документы: [контракты](03-contracts.md), [план](05-implementation-plan.md), [PR](06-extension-prs.md).

## Три контрольных состояния

| Состояние | Содержание | Для чего |
| --- | --- | --- |
| `upstream` | свежие GitHub исходники до изменений | Функциональная исходная точка |
| `clean-control` | разрешённые внутренние рефакторинги и удаление прежней телеметрии, ещё без новых фасадов/разметки | Чистая контрольная точка для измерения стоимости новой системы |
| `candidate` | тот же business code + фасады/разметка | Будущие owner PR |

Функциональные результаты сравниваются upstream → clean-control → candidate/off → candidate/diagnostic. Накладные расходы новой системы сравниваются **clean-control/off и candidate/off**. Обнаруженное ускорение после удаления прежнего таймера не считается доказательством бесплатности нового SDK.

Нельзя использовать разные курсы, параметры, пакетные версии или caches для пары A/B. Контрольный commit сохраняется до завершения проверки. Если в candidate появились другие business-изменения, создать соответствующий обновлённый clean-control; не сравнивать смешанные изменения.

## Проверки фасада и агентов

| Проверка | Ожидаемое поведение |
| --- | --- |
| Off identity | Фабрики возвращают исходные объекты функций; нет обращения к часам/агенту/hooks/файлам |
| Sync values/this/errors | Значения и this сохраняются; throw передаёт исходный объект ошибки |
| Async branches | Promise.all создаёт независимые дочерние контексты, сохраняются fulfilled values/rejection object |
| Lua multiple returns | Сохраняются nil и количество результатов |
| Lua recursion/tail calls/coroutines | Стек и счётчики не смешиваются между корутинами; unwinding не создаёт успешный end |
| Duplicate facade copies | Один агент на executor; нет дублей span/counter при разных install paths |
| Missing/invalid agent ABI | Диагностический запуск помечается invalid; обычный пакет работает самостоятельно |
| Telemetry failure | Не заменяет результат/ошибку курса; runner не объявляет измерения валидными |
| Exit/signal | Выходы и сигналы исходного инструмента сохраняются; доступный flush, явные partial данные |
| TS bootstrap | import.meta.main, относительные импорты, dynamic imports и args сохраняются |
| AST fixtures | Отдельные full/fragment walks, nested родитель, stop traversal false, изменения AST сохраняются |
| Coverage | Unsupported и skipped — явные; отсутствие наблюдения не равно 0 вызовов |

Не рассчитывать node_visits по количеству callback, размеру входного дерева или дополнительному обходу. В native traversal такой счётчик недоступен без отдельной инструментализации обходчика.

## Функциональная эквивалентность Java

Полные student и full дают одинаковый набор ожидаемых outputs, каталоги, ссылки, ответы, педагогические данные, навигацию и ZIP-содержимое. Сравнивать байты там, где результат детерминирован; в остальных случаях нормализовать только заранее перечисленные timestamps, временные пути и аналогичные технические поля. Не удалять произвольные различия из DOM ради прохождения проверки.

Нормализация — версионируемый allowlist в `src/analysis/outputs.ts`, с тестом, который сохраняет различия в учебном содержимом, target links и ответах. Сравнение ZIP выполняется по списку entries и распакованному содержимому; различающиеся служебные timestamps не скрывают разницу файлов.

Проверить, что internal agents, profiles, logs и scenario manifests не попали в публикуемый `_site`, course ZIP или распространяемые packages расширений.

## Benchmark и критерий off overhead

Нормативная цель R-16: стоимость новой системы в обычной сборке — не более **1%** по wall time против clean-control на одинаковой нагрузке. CPU/память — дополнительные диагностические показатели, не подмена wall threshold.

1. Подготовить зависимости и обе рабочие копии вне интервала. По одному исключаемому прогревочному запуску каждого варианта для контролируемого warm сравнения.
2. Выполнить 10 A/B пар для представительного документа/набора. Чередовать порядок AB/BA; записывать порядок и каждый результат. Это обязанность runner, не предположение о порядке команд Hyperfine.
3. Для пары вычислить `r = candidate_wall / control_wall`; отчёт содержит median(r), raw values и фиксированным seed рассчитанный 95% bootstrap interval медианы, 10 000 resamples.
4. `PASS`, если верхняя граница interval ≤ 1.01. `FAIL`, если нижняя > 1.01. Иначе `INCONCLUSIVE`.
5. При INCONCLUSIVE увеличить число до 30 пар либо документировать ограничение и продолжить обсуждение/измерения. Не объявлять PASS по точечной оценке. Если все значения равны, не выдумывать статистическую точность таймера.
6. Полные student/full: сначала 5 A/B пар каждого профиля; повторные сборки отдельно от clean-output. Тот же критерий и статус. Для шума разрешено увеличить до 30 пар; если это не выполнено, off-overhead acceptance остаётся INCONCLUSIVE.

Один проход полного курса доказывает функциональную работоспособность, но не доказывает overhead ≤ 1%. Не считать p95 по нескольким повторениям. Подробный trace/специальный Pandoc не участвуют в этом контрольном A/B.

Использовать Hyperfine 2 при наличии проверенных metrics `time_wall_clock,time_cpu,time_user,time_system,memory_peak_resident`, сохранять raw JSON. Отсутствующая метрика — unavailable, не ноль. Peak RSS — показатель, возвращённый измерителем; он **не** объявляется одновременной суммой RSS всего дерева процессов. Hardware counters в пилоте не обязательны.

Различать чистые outputs и холодный OS cache. Глобальная очистка кешей, изменение governor и остановка пользовательских процессов не требуются. Состояние машины фиксируется кратко; помехи/сбой не скрываются удалением неугодных результатов.

## Достоверность подробной карты

- Validate begin/end, sequence, ID uniqueness, родительские отношения, значения counter и область scope.
- Ошибка/убитый процесс оставляют aborted/incomplete, не успешное завершение.
- Frame/operation duration относится к своему clock domain. В первом этапе TS и Lua выводятся отдельно.
- Lua CPU interval измеряет CPU процесса во время операции, а не гарантированно только эту Lua-функцию.
- Samples показывают оценку CPU, не точные call counts. Частоты вызовов получаются от trace/разметки.
- События разных run не соединяются parent_span_id; experiment_id связывает только отчёты.
- Нельзя суммировать inclusive родитель и детей либо пересекающиеся async интервалы.

## Существующие owner checks

Повторно найти команды в свежих репозиториях. При подготовке наблюдались `quarto-course/tools/check-canonical.sh`, owner TS tests QRC/Publisher, Download `tools/check.sh`, PrairieLearn `tools/check-java*.sh`. Не запускать их без чтения аргументов и текущих инструкций и не переносить устаревшие результаты как свежие доказательства.

Финальная проверка: актуальные owner checks, проверка installable packages, все сценарии Java и ABI conformance. CI включать на финальных PR по действующим owner правилам; локальные проверки не заменяют обязательные GitHub checks.

## Итоговый отчёт

Перечислить refs/hashes, commands, profiles, cache policies, repeats, PASS/FAIL/INCONCLUSIVE, coverage, clocks, data validity, один подтверждённый bottleneck либо явное отсутствие обнаруженного bottleneck. Указать ссылки на PR и raw evidence. Не заявлять ускорение без ordinary benchmark после исправления.
