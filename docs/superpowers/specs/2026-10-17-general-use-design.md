# Простой измеряемый рендер и установка quarto-course-perf

`quarto-course-perf render` должен запускаться из каталога курса почти так же,
как `quarto render`. Первая целевая область — проекты пользователя на расширениях
Course-Tools, включая Java и Cybersecurity. Имя курса, его профили и структура
каталогов не должны быть условиями работы инструмента.

Команда устанавливается один раз через пакет Arch Linux. Основной README
объясняет установку, первый запуск и результат; устройство диагностики и
сравнительные эксперименты описываются отдельно.

Это проект следующего интерфейса. Существующий выпуск 1.0.0 его ещё не
предоставляет. Документы первоначального Java-пилота остаются историческими.

## Согласованные требования

- Название установленной команды и Arch-пакета — `quarto-course-perf`.
- Репозиторий сохраняет имя `quarto-course-performance`.
- Основной вызов — `quarto-course-perf render` из того каталога, где пользователь
  обычно вызывает `quarto render`.
- Нативные параметры Quarto, например `--profile student`, передаются без
  дополнительного JSON, регистрации курса или подготовки владельцев расширений.
- По умолчанию измеряется обычная сборка. Диагностика операций включается явно.
- Пользовательские исходники, установленные расширения, ветки и незакоммиченные
  изменения сохраняются. Обычные результаты рендера создаются штатно.
- README упрощается только в этом репозитории. Новые тексты — по-русски по
  [общему языковому правилу](https://github.com/Afonenko-Course-Tools/quarto-course/blob/main/docs/russian-language-policy.md).
- Существующие агенты, протокол событий и отчёты переиспользуются. Новый общий
  runtime и система исполнения произвольных программ не создаются.

## Основной интерфейс

Обычный запуск после установки:

```sh
quarto-course-perf render
quarto-course-perf render --profile student
quarto-course-perf render tasks --profile full
quarto-course-perf render theory/topic.qmd --to html
```

Профили `student` и `full` — примеры профилей конкретного курса. Допускаются
другие нативные профили и запуск без профиля. Quarto сам определяет проект,
настройки, вложенные проекты, входные документы и выходные файлы.

Параметры инструмента имеют префикс `--perf-`:

```sh
quarto-course-perf render --perf-mode summary --profile student
quarto-course-perf render --perf-mode cpu --profile student
quarto-course-perf render --perf-output "$HOME/measurements" --profile student
```

`--perf-mode` принимает `off`, `summary`, `cpu`; значение по умолчанию — `off`.
`--perf-output` задаёт родительский каталог отдельных запусков. В нём для каждого
запуска создаётся новый каталог; прежние измерения не перезаписываются.
При отсутствии параметра используется
`${XDG_STATE_HOME:-$HOME/.local/state}/quarto-course-perf/runs/<run-id>`.
Каталог по умолчанию расположен вне дерева курса. Если пользователь явно
выбирает `--perf-output` внутри проекта, он исключает этот каталог из нативных
входов/ресурсов Quarto; инструмент не изменяет конфигурацию курса за него.

Параметры `--perf-` читаются в начале после `render`; первый другой аргумент
начинает неизменяемую последовательность аргументов Quarto. Поддерживаются формы
`--perf-mode summary` и `--perf-mode=summary`. Префикс `--perf-` зарезервирован
инструментом: неизвестный или повторный его параметр в этой начальной части
даёт понятную ошибку до рендера. Разделитель `--` завершает собственные параметры
и удаляется; следующие аргументы передаются Quarto буквально. Последующий
нативный `--`, если он есть, сохраняется. Поэтому для нативного разделителя
используется `quarto-course-perf render -- -- <аргументы Quarto>`: первый
разделитель относится к оболочке, второй остаётся в argv Quarto.
Вызов `quarto-course-perf render --help` показывает справку нативного рендера;
`quarto-course-perf --help` объясняет измерение и собственные параметры.

`--help` и `--version` работают из любого каталога, без курса, Java-сценария,
сети и наличия Quarto. Версия читается из установленного приложения.

## Поведение измеряемого рендера

Простой путь выполняется в том же рабочем каталоге, что и обычный рендер.
Пользователь получает штатные выходные файлы Quarto в ожидаемых местах. Это
уточняет первоначальное предложение о копировании каждого запуска: копии нужны
там, где инструмент меняет исходники для диагностики или готовит эксперимент.

В обычном режиме запускается установленный `quarto render` с пользовательскими
аргументами. Инструмент сохраняет функциональные переменные окружения, настройки
Quarto, сеть, существующие результаты, cache/freeze и активные профили. Он не
добавляет очистку output, отдельный cache или `QUARTO_RUN_NO_NETWORK`.
Подготовка отчёта и проверка окружения выполняются вне измеряемого интервала.

Перед запуском проверяются конфликтующие переменные старой/новой телеметрии.
Инструмент явно сообщает о конфликте и способе его устранения, сохраняя
функциональные настройки. Он не должен молча менять выбранные пользователем
`QUARTO_DENO`, `QUARTO_PANDOC` или `QUARTO_SHARE_PATH`. В `off` они передаются
обычному Quarto; диагностика использует их как исходные исполняемые файлы,
если они поддерживаются, либо объясняет невозможность выбранного режима.

Стандартный вывод и ошибки Quarto показываются по мере поступления и
одновременно сохраняются. Служебные сообщения Performance идут в stderr,
сохраняя stdout для перенаправления. Весь вывод не удерживается в памяти до окончания
сборки. `stdin` остаётся доступен дочернему процессу. Терминальные возможности
и перенаправление вывода проверяются отдельно; сохранение журналов не должно
мешать интерактивной сборке.

До запуска создаётся отдельный каталог отчёта и проверяется доступ к записи.
В конце автоматически создаются `report.md` и `run.json`, печатаются длительность,
доступные CPU/пиковая память, статус сборки и путь к отчёту. Если измеритель
ресурсов отсутствует, CPU и память обозначаются как недоступные; время не
подменяет их. Отдельной команды `report` для первого использования не требуется.

Неуспешный Quarto возвращает свой исходный код. SIGINT/SIGTERM передаются
собственному дереву рендера, включая дочерние Deno/Pandoc. Перед финальным
отчётом инструмент ожидает остановки этого дерева, не затрагивая чужие процессы
терминала. Фактическое завершение сохраняется в отчёте. Ошибка
подготовки инструмента не выдаётся за ошибку Quarto. Если Quarto завершился
неуспешно, ошибка последующей записи отчёта не должна скрывать его код.
Если рендер успешен, но инструмент не смог сохранить обязательный отчёт,
команда завершается с собственным ненулевым кодом и объясняет причину.
То же правило действует при успешном рендере и повреждённой запрошенной
диагностике: потерянные ожидаемые журналы, события или CPU-профиль дают
ненулевой статус Performance. Отсутствие размеченных операций само по себе
не означает повреждения данных.

Метаданные включают исходные argv/cwd, версию инструмента и Quarto, режим,
доступные сведения Git и признак незакоммиченных изменений. Простой запуск
измеряет текущее рабочее состояние: ему не приписывается воспроизводимость
чистого закреплённого Git-эксперимента. Он работает и без `.git`.

## Диагностика расширений

`summary` и `cpu` используют существующие агенты и подготовленные служебные
файлы за пределами исходников курса. Установленные пакеты не заменяются
локальными checkout владельцев. Получение зависимостей и предварительная
подготовка служебных файлов находятся вне измеряемого интервала. Запуск и
импорт агентов внутри дочерних Quarto-процессов входят во время диагностики.

Сводка показывает только операции выбранных или фактически наблюдавшихся
расширений Course-Tools. Установленное расширение без нужной разметки
помечается соответствующим образом. Вызов справки, пропущенные из-за штатного
freeze вычисления и запуск без подходящих дочерних исполнителей не равны
потере ожидаемого журнала. Отсутствие наблюдений не превращается
в нулевую стоимость или заявление о полном покрытии. Если Quarto успешно
завершился, но диагностика неполна, оба состояния показываются раздельно.

Текущее преобразование TypeScript для `trace` переписывает выбранные модули.
Его применение к пользовательскому дереву запрещено. Полный существующий
режим `trace` сохраняется в расширенном интерфейсе изолированных экспериментов;
простой `render --perf-mode trace` объясняет доступный способ подробного анализа.
Не вводится урезанный режим с тем же именем и другим обещанием покрытия.

Длительность `summary`/`cpu` относится к диагностическому запуску. Сравнивать
скорость обычных версий и оценивать стоимость разметки нужно отдельными
измерениями `off`. Один рендер не даёт статистического заключения об ускорении.

## Обобщение существующих экспериментов

Существующие команды `sources`, `freeze`, `run`, `benchmark`, `report`, `verify`
переходят под `quarto-course-perf experiment`. Параметры расширенных сценариев
не усложняют разбор нативных аргументов простого `render`. Для разработки
сохраняется запуск через Deno из checkout с теми же подкомандами.

В новом контракте конфигурации явно задаётся репозиторий измеряемого проекта.
Подготовка не ищет `/Java`. Участие других источников и замена пакетов задаются
явно; сохранённые установленные пакеты не требуют обязательных checkout всех
владельцев. Неоднозначные назначения пакетов отклоняются до изменения копии.

Отдельное `courseProfile: student|full` удаляется: нативный профиль живёт в argv.
Число пар задаётся настройкой/параметром с единым значением по умолчанию,
не зависит от префикса `java-full-`. Порог допустимого замедления — явная
политика сравнительного эксперимента; исторические 1% остаются настройкой пилота.

Сравнение результатов по умолчанию строгое. Исторические Core/QRC-нормализации
используются только при явном выборе соответствующей проверки пилота.
Сырые свидетельства, отчёты и архив `docs/plan` не переписываются под новую схему.
Java-сценарии мигрируют однократно как примеры расширенного применения.

Новый интерфейс и конфигурация выпускаются как 2.0.0. Прежние команды 1.0.0
описываются в короткой инструкции перехода; параллельный слой старой схемы
не поддерживается.

## Устройство установленного приложения

Arch-пакет устанавливает:

| Путь | Назначение |
| --- | --- |
| `/usr/bin/quarto-course-perf` | Исполняемая команда, запускающая Deno |
| `/usr/lib/quarto-course-perf/` | Исходники TS/Lua, фасады, данные и зависимости приложения |
| `/usr/share/doc/quarto-course-perf/` | README, инструкция установки и примеры |

Для первой поставки используется дерево файлов с небольшой запускающей
оболочкой. Самостоятельный `deno compile` не является выбранной сборкой:
существующий backend читает и копирует TS/Lua-файлы, а помощник ресурсов
вызывает полноценный `deno run` через `Deno.execPath()`.

Приложение находит файлы относительно своего установленного расположения,
не относительно каталога курса и не через путь локального checkout.
Преобразование файловых URL учитывает пробелы и другие кодируемые символы.
Запускающая оболочка явно выбирает конфигурацию и lock-файл приложения,
сохраняя текущий каталог пользователя для Quarto. Она не читает случайный
`deno.json` курса как конфигурацию самого инструмента.

Версии npm-зависимостей закреплены lock-файлом. Их исходные архивы перечисляются
в `source` рецепта с точными версиями и проверяемыми контрольными суммами.
Пакет содержит подготовленный локальный `node_modules`; установленный runner
использует режим `manual` и `--cached-only`. Первый запуск не требует npm-загрузки и
не пишет в `/usr`. Проверка из каталога с посторонним `deno.json` и новым пустым
пользовательским Deno cache и запрещённой загрузкой модулей обязательна,
включая настоящий TS trace расширенного эксперимента. Хеши установленного
дерева до и после запуска должны совпадать. Это гарантия зависимостей инструмента;
обычный курс может иметь собственные сетевые зависимости.

Deno и Quarto устанавливаются отдельно и объявляются зависимостями пакета.
Выбранный пакет Quarto должен предоставлять зависимость `quarto`.
GNU time обеспечивает CPU/память и входит в зависимости Arch-поставки.
Hyperfine требуется только для сравнительных измерений; Git и unzip — для
соответствующих расширенных действий. Нужность этих инструментов проверяется
при выборе действия, а не при `render --help` или обычном измерении.

Пакет не устанавливает Quarto повторно, не изменяет его системные файлы и
не запускает курсы от root. Отсутствующую в исходниках лицензию нельзя
самостоятельно заменить выдуманной лицензией в метаданных пакета.

## Сборка и установка пакета Arch Linux

Результат реализации включает `packaging/arch/PKGBUILD`, запускающую оболочку
и `docs/arch-package.md`. Рецепт поддерживает сборку из опубликованного
исходного архива точной версии с SHA-256. Для проверки до выпуска собирается
локальный архив выбранного коммита с тем же составом; отдельный простой
сценарий подготовки создаёт каталог сборки и фиксирует хеш этого архива.
Пути из рабочего дерева разработчика в установленный пакет не попадают.

Целевой порядок после появления рецепта:

```sh
# Подготовка инструментов сборки Arch Linux.
sudo pacman -Syu --needed base-devel

# В подготовленном каталоге с PKGBUILD и точными исходниками.
makepkg -s

# Отдельная установка созданного пакета.
sudo pacman -U ./quarto-course-perf-2.0.0-1-any.pkg.tar.zst

# Проверка установленной команды из каталога своего курса.
quarto-course-perf --version
quarto-course-perf render --profile student
```

Конкретное имя файла берётся из вывода `makepkg --packagelist`; пример выше
соответствует версии 2.0.0, первому выпуску Arch-рецепта и независимому от
архитектуры составу исходников. Статус поддержки Linux x86-64 определяется
проверками, а `arch=('any')` описывает состав пакета.

`makepkg` выполняется обычным пользователем. `-s` разрешает установку
объявленных недостающих зависимостей через pacman. Если нужный Quarto
установлен из пользовательского рецепта, он предварительно оформляется как
пакет, предоставляющий `quarto`; наличие одного бинарного файла не заменяет
зависимость в базе pacman.

Инструкция также описывает проверку состава через `pacman -Qlp`, проверку
рецепта/пакета через `namcap`, повторную сборку при обновлении и удаление
через `sudo pacman -R quarto-course-perf`. Данные измерений в пользовательском
каталоге сохраняются при удалении приложения.

Публикация в AUR, установка на машину пользователя и выбор лицензии не входят
в подготовку рецепта и инструкции. Готовый локальный пакет проверяется без
обязательного изменения системной установки.

Основные правила рецепта и последовательность сборки сверяются с
[PKGBUILD(5)](https://man.archlinux.org/man/PKGBUILD.5.en) и
[makepkg(8)](https://man.archlinux.org/man/makepkg.8.en).
Управление локальными зависимостями соответствует документации
[Deno install](https://docs.deno.com/runtime/reference/cli/install/) и
[конфигурации Deno](https://docs.deno.com/runtime/reference/deno_json/).

## Документация

Основной README укладывается в короткий пользовательский маршрут: назначение,
установка, одна команда рендера, пример результата, выбор диагностики и ссылки
на подробности. Проверки разработчика идут после пользовательских инструкций.
Вступление не начинается с фасадов, Compiler API или внутренних часов.

Отдельные документы описывают Arch-пакет, диагностику и её ограничения,
сравнительные эксперименты, переход с 1.0.0 и разработку. Архив плана сохраняется
в неизменном составе с контрольными суммами; новая навигация явно называет его
историей Java-пилота. README не обещает доступность новой команды в старом теге.

## Проверка результата

1. В небольшом Quarto-проекте на Course-Tools без имени Java проходят обычный
   рендер и `quarto-course-perf render` без дополнительной конфигурации.
2. Java и Cybersecurity запускаются из привычных каталогов с их настоящими
   нативными параметрами. Фиксируются точные проверенные ревизии и установленные
   версии расширений. Незакоммиченные исходники не теряются.
3. Проверяются запуск без профиля, произвольный профиль, файл и каталог,
   пробелы в путях, параметры `--key=value`, перенаправление вывода и stdin.
4. Подтверждается передача cwd/argv/функционального окружения. Простая команда
   не очищает outputs/cache и не вводит запрет сети или дополнительные рендеры.
5. Ошибки Quarto, недоступный инструмент, конфликт диагностики, SIGINT/SIGTERM
   и невозможность записи отчёта дают различимые результаты и сохранённые
   сведения о фактическом завершении. Прерывание проверяется на рендере с
   дочерним процессом: после возврата команды он не продолжает запись.
6. `summary`/`cpu` сохраняют пользовательские TS/Lua и пакеты; отсутствие
   разметки/наблюдений отображается честно. `trace` доступен в изолированном
   эксперименте и не преобразует исходники простого рендера. Значимые результаты
   обычного Quarto и режимов `off`, `summary`, `cpu` сравниваются на представительном
   проекте, включая пользовательские runtime и Pandoc data-dir. Проверка не
   скрывает изменения содержимого общей нормализацией HTML.
7. Обобщённый эксперимент работает с другим именем репозитория и явной заменой
   пакетов. Сохраняются проверки SHA, хешей runtime, ограничений путей,
   повторных запусков и прежние проверки backend.
8. Рецепт действительно создаёт Arch-пакет. Проверяется состав и запуск из
   временно распакованного установленного дерева, затем в чистом окружении
   Arch, если оно доступно. Проверка системного pacman-install учитывается
   отдельно и не заявляется по результату одной распаковки.
9. Установленный инструмент работает из чужого каталога и с чистым cache,
   находит Lua/TS/registry, не пишет в `/usr` и не требует checkout Performance.
10. Перед выпуском проходят подходящие локальные проверки и CI на финальном
    исходнике. Выпуск включает инструкцию перехода и проверенный Arch-рецепт;
    исторические теги и Releases сохраняются.
