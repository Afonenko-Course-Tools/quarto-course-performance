# Простой измеряемый рендер и установка quarto-course-perf

`quarto-course-perf render` должен запускаться из каталога курса почти так же,
как `quarto render`. Первая целевая область — проекты пользователя на расширениях
Course-Tools; тестовая база текущей реализации — Java. Имя курса, его профили
и структура каталогов не должны быть условиями работы инструмента.

Команда устанавливается один раз через пакет Arch Linux. Основной README
объясняет установку, первый запуск и результат; устройство диагностики и
сравнительные эксперименты описываются отдельно.

Это проект следующего интерфейса. Существующий выпуск 1.0.0 его ещё не
предоставляет. Документы первоначального Java-пилота остаются историческими.
Задачи реализации и приёмки собраны в
[общем плане](../plans/2026-10-17-general-use-implementation.md).

## Согласованные требования

- Название установленной команды и Arch-пакета — `quarto-course-perf`.
- Репозиторий сохраняет имя `quarto-course-performance`.
- Основной вызов — `quarto-course-perf render` из того каталога, где пользователь
  обычно вызывает `quarto render`.
- Нативные параметры Quarto, например `--profile student`, передаются без
  дополнительного JSON, регистрации курса или подготовки владельцев расширений.
- По умолчанию измеряется обычная сборка. Диагностика операций включается явно.
- Результаты измерений по умолчанию сохраняются в `.quarto/course-perf` текущего
  Quarto-проекта; каждый запуск получает отдельный каталог.
- При простом рендере пользовательские исходники, установленные расширения,
  ветки и незакоммиченные изменения сохраняются. Обычные результаты рендера
  создаются штатно.
- README упрощается только в этом репозитории. Новые тексты — по-русски по
  [общему языковому правилу](https://github.com/Afonenko-Course-Tools/quarto-course/blob/main/docs/russian-language-policy.md).
- Существующие агенты, протокол событий и отчёты переиспользуются. Новый общий
  runtime и система исполнения произвольных программ не создаются.
- Основной визуализатор — Perfetto; Speedscope используется дополнительно для
  существующих V8 CPU-профилей. Совместимость обеспечивается экспортом данных.
- Инструмент не обновляет пакеты курса автоматически. Наблюдение установленной
  разметки и явная замена пакетов в расширенном эксперименте — разные действия.
- Для новой диагностики допускается требование перейти на согласованные новые
  выпуски нужных расширений и их мостов. Подготовка тестовой Java выполняется
  отдельной явной задачей до основной интеграционной приёмки.

## Проверенная база и границы приёмки

Аудит 17 октября 2026 года сверил текущие исходники владельцев, включая
Performance `409afa12dddee5cf20528efef24e7e0639fffcc7`,
Core `aebf6f4580c0bd5e9468498e840221619fc69e5f` и
PrairieLearn `69924dbda56ed55fb556f2e0932565eafbdb6448`.
Это исходная точка планирования; перед реализацией проверяются актуальные
контракты и явно закрепляются новые исходные SHA без подмены прежних свидетельств.

Исходная точка подготовки Java — текущий
[черновой PR16 Java](https://github.com/BSU-RFCT-Afonenko-Courses/Java/pull/16),
на момент аудита `7a5a2d5e700261868827465add54970f0dfd025e`.
В нём установлены Core/Presentation/Navigation 7.1.0 с явно сохранёнными
кандидатными правками; это не побайтная установка чистого тега 7.1.0.
PrairieLearn также имеет собственные кандидатные правки. Версию 7.2.0 этому
исходному дереву не приписывают. Перед подготовкой перепроверяются head PR,
установленные дескрипторы, исходные коммиты и хеши наложений.

Основная тестовая база — Java после отдельного перехода на согласованные новые
выпуски нужных владельцев с обновлёнными мостами. Перед заменой пакетов
сопоставляются функции кандидатных правок с Core 7.2.0 и PrairieLearn 7.1.0:
фиксируется, какие изменения уже вошли в выпуски, а какие ещё требуют переноса
и выпуска у владельца. Функциональность кандидатных правок сохраняется;
механическое стирание наложений или повторное применение уже вошедших изменений
не допускается. Полные пакеты обновляются штатным установщиком Java во всех
соответствующих нативных проектах; отдельные файлы установленных пакетов вручную
не подменяются. Сохраняются сведения о происхождении прежней и новой установки.
Точные итоговые версии, исходные SHA, хеши пакетов и подготовленный SHA Java
фиксируются после этой подготовки и закрепляются на весь эксперимент.
Обновление выполняется до основной интеграционной приёмки и не является
автоматическим действием `quarto-course-perf render`.

По прямому указанию пользователя обновление Cybersecurity, его рендеры,
приёмочные тесты и создание нового PR отложены. Существующие PR, ветки и рабочие
деревья курса сохраняются. Общий интерфейс остаётся независимым от имени Java;
небольшие самостоятельные Quarto-проекты проверяют эту независимость без
обновления другого пользовательского курса.

## Основной интерфейс

Обычный запуск после установки:

```sh
quarto-course-perf render
quarto-course-perf render --profile student
quarto-course-perf render tasks --profile full
quarto-course-perf render theory/topic.qmd --to html
```

Профили `student` и `full` — примеры профилей конкретного курса. Допускаются
другие нативные профили и запуск без профиля. Quarto сам определяет проект,
настройки, вложенные проекты, входные документы и выходные файлы.

Параметры инструмента имеют префикс `--perf-`:

```sh
quarto-course-perf render --perf-mode summary --profile student
quarto-course-perf render --perf-mode cpu --profile student
quarto-course-perf render --perf-output "$HOME/measurements" --profile student
```

`--perf-mode` принимает `off`, `summary`, `cpu`; значение по умолчанию — `off`.
`--perf-output` задаёт родительский каталог отдельных запусков. В нём для каждого
запуска создаётся новый каталог; прежние измерения не перезаписываются.
При отсутствии параметра используется `<project-root>/.quarto/course-perf/runs/<run-id>`:

```text
.quarto/
  course-perf/
    runs/
      <run-id>/
        report.md
        run.json
        stdout.log
        stderr.log
```

Корень измеряемого проекта определяется нативным `quarto inspect`, включая
запуск из подпапки и явно переданную цель в другом проекте. Самостоятельный
вложенный Quarto-проект получает свою `.quarto/course-perf`; обычная подпапка остаётся
в области своего проекта. Для отдельного документа вне проекта используется
каталог документа. При этом cwd и argv самого рендера не меняются.
`--output-dir` Quarto не выбирает расположение измерений. Относительный
`--perf-output` разрешается от исходного cwd пользователя.

Вызов `inspect` имеет собственный контракт аргументов: весь argv рендера ему
не передаётся. Узкий определитель проекта выделяет подтверждённую цель и только
поддерживаемые `inspect` параметры контекста, сохраняя полный исходный argv
для самого `render`.
Его проверки различают путь цели, значения параметров и разделители, включая
профили, `--to`, `--output-dir`, формы `--key=value` и цель в другом проекте.

Путь к отчёту печатается после запуска. Используется обычное исключение
`.quarto/` из Git проекта. Для отдельного документа оно может отсутствовать;
инструкция показывает соответствующую запись. Сам инструмент не редактирует
`.gitignore` курса. Если проект недоступен для записи, команда объясняет
проблему и предлагает `--perf-output`, не переносит данные домой без указания.

`.quarto` — служебный каталог Quarto. Результаты внутри него являются локальными
очищаемыми данными: инструмент не перезаписывает прежние запуски, но удаление
или штатная очистка всей `.quarto` может удалить их. Для долговременного хранения
используется `--perf-output` с каталогом вне `.quarto`.

В проверенном Quarto 1.11.5 обычные рендеры проектов, повторные запуски и
`render --clean` сохраняют такой подкаталог. Однофайловый рендер с `--output-dir`
может включать очистку всей `.quarto`; это отдельное поведение `forceClean`,
описанное в [исходниках Quarto](https://github.com/quarto-dev/quarto-cli/blob/main/src/command/render/project.ts).
Инструмент не добавляет `--no-clean` ради сохранения своей истории.

Штатные входы и ресурсы Quarto исключают `.quarto`; проверяется также маска
`resources: ["**"]`. Для явно выбранного другого `--perf-output` проверяется,
не захватывают ли его нативные входы или ресурсы, и при необходимости предлагается
исключение либо иной путь. Конфигурация курса не переписывается.
Произвольные авторские hooks могут копировать файлы самостоятельно и сохраняют
свою ответственность за выбранные результаты.

Параметры `--perf-` читаются в начале после `render`; первый другой аргумент
начинает неизменяемую последовательность аргументов Quarto. Поддерживаются формы
`--perf-mode summary` и `--perf-mode=summary`. Префикс `--perf-` зарезервирован
инструментом: неизвестный или повторный его параметр в этой начальной части
даёт понятную ошибку до рендера. Разделитель `--` завершает собственные параметры
и удаляется; следующие аргументы передаются Quarto буквально. Последующий
нативный `--`, если он есть, сохраняется. Поэтому для нативного разделителя
используется `quarto-course-perf render -- -- <аргументы Quarto>`: первый
разделитель относится к оболочке, второй остаётся в argv Quarto.
Вызов `quarto-course-perf render --help` показывает справку нативного рендера;
`quarto-course-perf --help` объясняет измерение и собственные параметры.

`--help` и `--version` работают из любого каталога, без курса, Java-сценария,
сети и наличия Quarto. Версия читается из установленного приложения.

## Поведение измеряемого рендера

Простой путь выполняется в том же рабочем каталоге, что и обычный рендер.
Пользователь получает штатные выходные файлы Quarto в ожидаемых местах. Это
уточняет первоначальное предложение о копировании каждого запуска: копии нужны
там, где инструмент меняет исходники для диагностики или готовит эксперимент.

В обычном режиме запускается установленный `quarto render` с пользовательскими
аргументами. Инструмент сохраняет функциональные переменные окружения, настройки
Quarto, сеть, существующие результаты, cache/freeze и активные профили. Он не
добавляет очистку output, отдельный cache или `QUARTO_RUN_NO_NETWORK`.
Подготовка отчёта и проверка окружения выполняются вне измеряемого интервала.

Этот запуск имеет отдельный путь исполнения от существующего `executeScenario`:
подготовка изолированного эксперимента, очистка и политика его окружения не
переносятся в простой `render`. Общими остаются узкие средства запуска процесса,
измерения ресурсов и подготовки отчёта, если они сохраняют нативную семантику.

Перед запуском проверяются конфликтующие переменные старой/новой телеметрии.
Инструмент явно сообщает о конфликте и способе его устранения, сохраняя
функциональные настройки. Он не должен молча менять выбранные пользователем
`QUARTO_DENO`, `QUARTO_PANDOC` или `QUARTO_SHARE_PATH`. В `off` они передаются
обычному Quarto; диагностика использует выбранные исполняемые файлы и каталоги,
если они поддерживаются, либо объясняет невозможность выбранного режима.
Проверка возможностей и свидетельства подготовки относятся именно к эффективным
путям с учётом этих переопределений. Пользовательские Pandoc `--data-dir`
и `init.lua` сохраняют своё поведение: установка агента должна быть совместима
с ними, а не подменять их служебным каталогом или файлом. Для неподдерживаемой
комбинации диагностика даёт явную ошибку до рендера.

Стандартный вывод и ошибки Quarto показываются по мере поступления и
одновременно сохраняются. Служебные сообщения Performance идут в stderr,
сохраняя stdout для перенаправления. Весь вывод не удерживается в памяти до окончания
сборки. `stdin` остаётся доступен дочернему процессу. Терминальные возможности
и перенаправление вывода проверяются отдельно; сохранение журналов не должно
мешать интерактивной сборке.

До запуска проверяется возможность сохранить результат по выбранному пути.
Журналы, профили, агенты и промежуточный отчёт текущего запуска собираются в
отдельном временном каталоге вне дерева проекта и `.quarto`. Существующий файл
вместо служебного каталога, символическая ссылка в его пути и пересечение с
output-dir Quarto дают понятную ошибку без перезаписи.

После завершения всего дерева рендера готовый запуск сохраняется в
`.quarto/course-perf/runs/<run-id>`; родительские каталоги при необходимости
создаются заново. Очистка scratch Quarto не должна уничтожить данные текущего
измерения. Сохранность более старых запусков при очистке `.quarto` не обещается.
Если сохранение результата не удалось, временные данные остаются доступны,
а их фактический путь выводится пользователю. Соседние служебные каталоги Quarto
не изменяются и не восстанавливаются.
После переноса все ссылки отчёта, профилей, манифеста и производных экспортов
должны открываться из конечного каталога. Пути к артефактам относительно запуска
переносятся вместе с ним; абсолютные исходные пути пользователя и среды исполнения
сохраняются как сведения о запуске и не переписываются общей заменой строк.

В конце автоматически создаются `report.md` и `run.json`, печатаются длительность,
доступные CPU/пиковая память, статус сборки и путь к отчёту. Если измеритель
ресурсов отсутствует, CPU и память обозначаются как недоступные; время не
подменяет их. Отдельной команды `report` для первого использования не требуется.

Неуспешный Quarto возвращает свой исходный код. SIGINT/SIGTERM передаются
собственному дереву рендера, включая дочерние Deno/Pandoc. Перед финальным
отчётом инструмент ожидает остановки этого дерева, не затрагивая чужие процессы
терминала. Фактическое завершение сохраняется в отчёте. Ошибка
подготовки инструмента не выдаётся за ошибку Quarto. Если Quarto завершился
неуспешно, ошибка последующей записи отчёта не должна скрывать его код.
Если рендер успешен, но инструмент не смог сохранить обязательный отчёт,
команда завершается с собственным ненулевым кодом и объясняет причину.
То же правило действует при успешном рендере и повреждённой запрошенной
диагностике: потерянные ожидаемые журналы, события или CPU-профиль дают
ненулевой статус Performance. Отсутствие размеченных операций само по себе
не означает повреждения данных.

Приёмка сигналов и остановки дерева — отдельная обязательная работа.
На момент аудита существующий тест SIGTERM падает с Deno 2.7.14 и 2.9.7;
действующий backend не считается подтверждением этого требования.
Нужны проверки SIGINT и SIGTERM с дочерним процессом и сохранением частичных
данных после завершения всего собственного дерева.
На Linux рендер получает отдельную сессию и группу процессов через штатный
`setsid` из `util-linux`; пересылка сигналов ограничена этой группой.
Новая общая среда исполнения для этого не создаётся.

Метаданные включают исходные argv/cwd, версию инструмента и Quarto, режим,
доступные сведения Git и признак незакоммиченных изменений. Состояние Git
фиксируется до создания текущего каталога измерения. Служебная `.quarto/course-perf`
учитывается отдельно от пользовательских исходников и на повторных запусках.
Простой запуск
измеряет текущее рабочее состояние: ему не приписывается воспроизводимость
чистого закреплённого Git-эксперимента. Он работает и без `.git`.

Один общий построитель результата запуска формирует отчёт и артефакты; адаптеры
простого рендера и эксперимента передают ему свои факты и политику. Раздельные
копии агрегирования, оценки качества и формирования ссылок не создаются.
Новый конфигурационный контракт, манифест источников, `run.json` и агрегированный
`summary.json` имеют `schema_version: 2`. Они описывают исходные параметры,
завершение, ресурсы, артефакты, происхождение данных, покрытие и качество.
Сырые Event и сводки отдельных исполнителей сохраняют `schema_version: 1`,
мост — ABI 1. Версия производного экспорта задаётся отдельно: сопроводительный
файл `export.json` имеет `schema_version: 1`, формат `chrome-trace-event-json`,
перечень файлов, исходные IDs и сведения о качестве. Сам Chrome Trace сохраняет
нативную оболочку формата. Исторические сырые данные и свидетельства не
переписываются; чтение старых неверсионированных результатов допускается
только явным импортом через отдельный адаптер.

## Диагностика расширений

`summary` и `cpu` используют существующие агенты, устанавливая их через
проверенные публичные точки Quarto/Pandoc. Во время запуска данные и
служебные файлы агентов находятся во внешнем временном каталоге;
готовые отчёты и журналы сохраняются в `.quarto/course-perf`. Пользовательские
TS/Lua-файлы не изменяются. Установленные пакеты не заменяются
локальными checkout владельцев. Получение зависимостей и предварительная
подготовка служебных файлов находятся вне измеряемого интервала. Запуск и
импорт агентов внутри дочерних Quarto-процессов входят во время диагностики.

Текущий backend изменяет внутреннюю функцию Quarto `run_emulated_filter` также
для `summary`/`cpu`. В простом пути эта зависимость устраняется. Наблюдение
интервала внутреннего исполнения фильтра допускается только как ограниченный
явно выбранный расширенный эксперимент с закреплёнными хешами среды исполнения
и проверкой возможностей; оно не является условием установки агента или
обещанием простого рендера.

Сводка различает установленные пакеты (`installed`), наличие в них разметки
(`instrumented`) и фактически записанные операции (`observed`). Реестр операций
описывает доступную разметку, а не фактический состав курса или полноту запуска.
Установленное расширение без нужной разметки помечается соответствующим образом.
Print, Moodle и Cloud по проверенным исходникам такой разметки не имеют;
общий агент не превращает их внутренние операции в наблюдённые.
Вызов справки, пропущенные из-за штатного freeze вычисления и запуск без
подходящих дочерних исполнителей не равны потере ожидаемого журнала.
Отсутствие наблюдений не превращается
в нулевую стоимость или заявление о полном покрытии. Если Quarto успешно
завершился, но диагностика неполна, оба состояния показываются раздельно.
Ошибка отсутствующего свидетельства запуска определяется для исполнителя
или профиля, который действительно ожидался по подтверждённому запуску.
Пустой список исполнителей сам по себе не означает повреждённую диагностику.

Контекст сохраняется в существующей сырой схеме: переданный `createMetrics`
или `create_metrics` идентификатор расширения записывается как
`attributes.extension_id`, а известный идентификатор документа — в существующее
поле `document_id`. В рамках ABI 1 в `OperationSpec` добавляются только
необязательные `attributes` и `document_id`;
сигнатуры методов и обязательные поля не меняются. Новый фасад связывает
ID расширения с операциями. Старый агент может проигнорировать эти добавления,
сохранив прежние измерения; со старым фасадом новый агент не выдаёт отсутствующий
ID расширения за записанный. Атрибуция старого `operation_id` по префиксу допустима
только с явным признаком `derived` и не подменяет исходные события.
Документ определяется только из доступного публичного Pandoc-контекста или
явного контекста владельца; неизвестное значение остаётся неизвестным.
Имя процесса, соседний документ и порядок событий не создают документный ID.
Совместимость старого и нового моста/агента проверяется небольшими отдельными
примерами там, где это недорого. Основная интеграционная приёмка использует
обновлённые мосты и не требует повторения всей матрицы на прежней установке.

Сохраняется точное поведение старого моста без агента: в `off` либо без режима
возвращаются исходная функция и исходный объект окружения; при отсутствии или
несовместимости агента в запрошенном режиме регистрируется прежняя ABI-ошибка
и возвращается тот же безопасный фасад без измерения. После установки
согласованного пакета контекст не требует отдельной подготовки при каждом
рендере или новой общей зависимости для владельца.
В TS невозможность прочитать переменную режима также сохраняет прежнее
возвращение исходной функции и исходного окружения без регистрации ABI-ошибки.

TS `childEnv` и Lua `child_env` используют одну семантику причинности: текущий
родитель заменяет унаследованный, а при отсутствии активного интервала устаревший
`COURSE_PERF_PARENT_SPAN_ID` удаляется. ID процесса может подтвердить отношение
процессов, но не точную связь операций. Дочерние команды без подтверждённой
границы операции остаются `unlinked`; временное соседство не создаёт причинную
стрелку. Область Lua `trace` выбирается по нормализованной идентичности файлов
вместо совпадения подстроки пути; это относится только к явно выбранному
расширенному `trace`.

Реестр синхронизируется с проверенными исходниками владельцев: добавляются
`course-navigation.filter.handler.Pandoc` и
`course-site.infrastructure.navigation.addressNavigation`. Аудит не обнаружил
удалённых зарегистрированных символов Core/PrairieLearn, поэтому их прежняя
разметка не объявляется отсутствующей. Достаточна узкая проверка соответствия
реестра исходникам; новая общая среда исполнения реестра или обязательная генерация
метаданных при запуске курса не вводятся.

Текущее преобразование TypeScript для `trace` переписывает выбранные модули.
Его применение к пользовательскому дереву запрещено. Полный существующий
режим `trace` сохраняется в расширенном интерфейсе изолированных экспериментов;
простой `render --perf-mode trace` объясняет доступный способ подробного анализа.
Не вводится урезанный режим с тем же именем и другим обещанием покрытия.

Длительность `summary`/`cpu` относится к диагностическому запуску. Сравнивать
скорость обычных версий и оценивать стоимость разметки нужно отдельными
измерениями `off`. Один рендер не даёт статистического заключения об ускорении.

## Визуализация и машинный анализ

Perfetto служит основным просмотрщиком общей картины диагностического запуска.
Первичные JSON/JSONL, сведения о качестве и исходниках сохраняются независимо
от просмотрщика. Для Perfetto создаётся производный Chrome Trace Event JSON;
подключать его SDK к курсам или расширениям не требуется.

Экспорт содержит понятные названия процессов и логических исполнителей,
доступные сведения об операциях/документах/расширениях в названиях и атрибутах интервалов, исходные
идентификаторы и статусы ошибок. Числовые `pid/tid` однозначно сопоставляются
исходным IDs; логические дорожки не выдаются за реальные потоки ОС.
Параллельные интервалы без отношения родительства не изображаются вложенными
вызовами. Подтверждённые связи родителей и потомков показываются стрелками
только при сопоставимых часах. Связь означает записанное логическое отношение,
а не отдельно измеренное время передачи управления или ожидания.

`wall.trace.json` показывает операции с доступной калибровкой времени.
Данные без такой калибровки получают отдельные локальные представления.
`lua-cpu.trace.json` остаётся отдельным: CPU каждого Lua-исполнителя имеет
локальную шкалу и не означает синхронность с другими дорожками. Причинные IDs
между несопоставимыми шкалами сохраняются в JSON без временных стрелок.

До агрегирования и экспорта проверяются парные границы интервалов: совпадают
эксперимент, запуск, процесс, исполнитель, `span_id`, операция и часы; конец
не предшествует началу. Дубли границ, конфликтующие идентификаторы, неверные поля
и незавершённые интервалы отражаются в качестве данных. Исходные строки
сохраняются, но из них не создаются вымышленные интервалы или причинные связи.
Повреждение одной записи не должно молча скрывать остальные исходные данные.

Существующие счётчики без отметок времени остаются агрегатами в `summary.json`.
Пиковая память и общее CPU-время также остаются итоговыми значениями.
Временные графики по этим значениям не выдумываются; дополнительный сбор
периодических измерений не входит в этот этап.
Событие `counter` с дельтой и итог того же счётчика в сводке того же исполнителя
представляют два свидетельства одного измерения: они сверяются, а не
складываются. Версионированная сводка явно определяет источник, смысл
`delta`/`total`, область исполнителя и качество каждого агрегата.

Speedscope открывает существующие `profiles/<process-id>/cpu.cpuprofile`
режима `cpu`. Отдельный экспортёр Speedscope не нужен. В отчёте перечисляются
только реально сохранённые профили, с процессом и качеством данных.

После диагностического рендера автоматически сохраняются совместимые файлы,
а `report.md` содержит ссылки на них и короткие инструкции открытия в Perfetto
и Speedscope. В режиме `off` остаются внешние измерения и обычный отчёт;
пустая трасса не выдаётся за наблюдение внутренних операций.
Установка просмотрщика не является условием измерения. Инструкция включает
открытие локального файла в браузере и использование локально размещённого UI.

Совместимость проверяется не только структурой JSON, но и фактическим импортом
контрольного примера с процессами, асинхронными перекрытиями и связями в Perfetto.
V8 CPU-профиль открывается в Speedscope отдельно. В отчёте проверки фиксируются
версии просмотрщиков, качество исходных данных и ограничения отображения.
Исходники и результаты существующего Java-пилота не переписываются.

Отдельный [план визуализации](../plans/2026-10-17-perfetto-visualization.md)
описывает задачи и проверки. Основа совместимости — официальная документация
[импорта Perfetto](https://perfetto.dev/docs/getting-started/other-formats),
[собственных данных Perfetto](https://perfetto.dev/docs/getting-started/converting)
и [форматов Speedscope](https://github.com/jlfwong/speedscope/wiki/Importing-from-custom-sources).

## Обобщение существующих экспериментов

Существующие команды `sources`, `freeze`, `run`, `benchmark`, `report`, `verify`, `capabilities`
переходят под `quarto-course-perf experiment`. Параметры расширенных сценариев
не усложняют разбор нативных аргументов простого `render`. Для разработки
сохраняется запуск через Deno из checkout с теми же подкомандами.

В новом контракте конфигурации явно задаётся репозиторий измеряемого проекта.
Подготовка не ищет `/Java`. Участие других источников и замена пакетов задаются
явно; сохранённые установленные пакеты не требуют обязательных checkout всех
владельцев. Неоднозначные назначения пакетов отклоняются до изменения копии.
Каждая замена имеет уникальное назначение внутри выбранного проекта;
остальные установленные пакеты сохраняются. Исходный проект и каждый
заменяющий пакет имеют явно указанное происхождение, закреплённую ревизию
и проверяемый хеш. Зависимости проверяются для выбранного действия:
рендер не требует средств подготовки чужих исходников или `benchmark`.

Отдельное `courseProfile: student|full` удаляется: нативный профиль живёт в argv.
Число пар задаётся настройкой/параметром с единым значением по умолчанию,
не зависит от префикса `java-full-`. Порог допустимого замедления — явная
политика сравнительного эксперимента; исторические 1% остаются только явно
выбранной настройкой Java-пилота.

Сравнение результатов по умолчанию строгое. Исторические Core/QRC-нормализации
используются только при явном выборе соответствующей проверки Java-пилота;
иная нормализация результатов также требует явного выбора и сохраняет
исходные файлы вместе с описанием преобразования.
Сырые свидетельства, отчёты и архив `docs/plan` не переписываются под новую схему.
Java-сценарии мигрируют однократно как примеры расширенного применения.
При подготовке новых снимков/копий и хешей исходников исключается служебная
`.quarto/course-perf`, чтобы результаты измерений не попадали во входы следующего
эксперимента. Старые сохранённые хеши не пересчитываются задним числом.

Новый интерфейс и конфигурация выпускаются как 2.0.0. Прежние команды 1.0.0
описываются в короткой инструкции перехода; параллельный слой старой схемы
не поддерживается.

## Устройство установленного приложения

Arch-пакет устанавливает:

| Путь | Назначение |
| --- | --- |
| `/usr/bin/quarto-course-perf` | Исполняемая команда, запускающая Deno |
| `/usr/lib/quarto-course-perf/` | Исходники TS/Lua, фасады, данные и зависимости приложения |
| `/usr/share/doc/quarto-course-perf/` | README, инструкция установки и примеры |

Для первой поставки используется дерево файлов с небольшой запускающей
оболочкой. Самостоятельный `deno compile` не является выбранной сборкой:
существующий backend читает и копирует TS/Lua-файлы, а помощник ресурсов
вызывает полноценный `deno run` через `Deno.execPath()`.

Приложение находит файлы относительно своего установленного расположения,
не относительно каталога курса и не через путь локального checkout.
Преобразование файловых URL учитывает пробелы и другие кодируемые символы.
Запускающая оболочка явно выбирает конфигурацию и lock-файл приложения,
сохраняя текущий каталог пользователя для Quarto. Она не читает случайный
`deno.json` курса как конфигурацию самого инструмента.

Версии npm-зависимостей закреплены lock-файлом. Их исходные архивы перечисляются
в `source` рецепта с точными версиями и проверяемыми контрольными суммами.
Пакет содержит подготовленный локальный `node_modules`; установленный runner
использует режим `manual` и `--cached-only`. Первый запуск не требует npm-загрузки и
не пишет в `/usr`. Проверка из каталога с посторонним `deno.json` и новым пустым
пользовательским Deno cache и запрещённой загрузкой модулей обязательна,
включая настоящий TS trace расширенного эксперимента. Хеши установленного
дерева до и после запуска должны совпадать. Это гарантия зависимостей инструмента;
обычный курс может иметь собственные сетевые зависимости.

Deno и Quarto устанавливаются отдельно и объявляются зависимостями пакета.
Выбранный пакет Quarto должен предоставлять зависимость `quarto`.
GNU time обеспечивает CPU/память и входит в зависимости Arch-поставки.
`util-linux` предоставляет `setsid` для собственной группы процессов рендера
и также входит в зависимости; наличие команды проверяется для выбранного
пути запуска.
Hyperfine требуется только для сравнительных измерений; Git и unzip — для
соответствующих расширенных действий. Нужность этих инструментов проверяется
при выборе действия, а не при `render --help` или обычном измерении.

Пакет не устанавливает Quarto повторно, не изменяет его системные файлы и
не запускает курсы от root. Отсутствующую в исходниках лицензию нельзя
самостоятельно заменить выдуманной лицензией в метаданных пакета.

## Сборка и установка пакета Arch Linux

Результат реализации включает `packaging/arch/PKGBUILD`, запускающую оболочку
и `docs/arch-package.md`. Рецепт поддерживает сборку из опубликованного
исходного архива точной версии с SHA-256. Для проверки до выпуска собирается
локальный архив выбранного коммита с тем же составом; отдельный простой
сценарий подготовки создаёт каталог сборки и фиксирует хеш этого архива.
Пути из рабочего дерева разработчика в установленный пакет не попадают.

Целевой порядок после появления рецепта:

```sh
# Подготовка инструментов сборки Arch Linux.
sudo pacman -Syu --needed base-devel

# В подготовленном каталоге с PKGBUILD и точными исходниками.
makepkg -s

# Отдельная установка созданного пакета.
sudo pacman -U ./quarto-course-perf-2.0.0-1-any.pkg.tar.zst

# Проверка установленной команды из каталога своего курса.
quarto-course-perf --version
quarto-course-perf render --profile student
```

Конкретное имя файла берётся из вывода `makepkg --packagelist`; пример выше
соответствует версии 2.0.0, первому выпуску Arch-рецепта и независимому от
архитектуры составу исходников. Статус поддержки Linux x86-64 определяется
проверками, а `arch=('any')` описывает состав пакета.

`makepkg` выполняется обычным пользователем. `-s` разрешает установку
объявленных недостающих зависимостей через pacman. Если нужный Quarto
установлен из пользовательского рецепта, он предварительно оформляется как
пакет, предоставляющий `quarto`; наличие одного бинарного файла не заменяет
зависимость в базе pacman.

Инструкция также описывает проверку состава через `pacman -Qlp`, проверку
рецепта/пакета через `namcap`, повторную сборку при обновлении и удаление
через `sudo pacman -R quarto-course-perf`. Данные измерений в `.quarto/course-perf`
проектов и явно выбранных каталогах сохраняются при удалении приложения.

Публикация в AUR, установка на машину пользователя и выбор лицензии не входят
в подготовку рецепта и инструкции. Готовый локальный пакет проверяется без
обязательного изменения системной установки.

Основные правила рецепта и последовательность сборки сверяются с
[PKGBUILD(5)](https://man.archlinux.org/man/PKGBUILD.5.en) и
[makepkg(8)](https://man.archlinux.org/man/makepkg.8.en).
Управление локальными зависимостями соответствует документации
[Deno install](https://docs.deno.com/runtime/reference/cli/install/) и
[конфигурации Deno](https://docs.deno.com/runtime/reference/deno_json/).

## Проверка результата

1. В небольшом Quarto-проекте на Course-Tools без имени Java проходят обычный
   рендер и `quarto-course-perf render` без дополнительной конфигурации.
2. До основной интеграционной приёмки отдельная задача переводит Java
   с перепроверенной исходной точки PR16 на согласованные новые полные пакеты
   нужных владельцев и мостов. Проверяется сохранение функций кандидатных правок
   и учитывается их включение в Core 7.2.0/PrairieLearn 7.1.0. Штатный установщик
   Java обновляет все нужные копии; фиксируются итоговые версии, исходные SHA,
   хеши и происхождение пакетов, подготовленный SHA Java. На этой базе проходят
   рендеры из привычных каталогов с настоящими нативными параметрами.
   Незакоммиченные исходники не теряются. Cybersecurity в эту приёмку не входит.
3. Проверяются запуск без профиля, произвольный профиль, файл и каталог,
   пробелы в путях, параметры `--key=value`, перенаправление вывода и stdin.
   Два проекта сохраняют отчёты раздельно в своих `.quarto/course-perf`. Проверяются
   обычная подпапка, самостоятельный вложенный проект, цель в другом проекте
   и отдельный документ; нативные значения параметров не принимаются за путь.
   `render --help` обходит поиск места для отчёта.
4. Подтверждается передача cwd/argv/функционального окружения. Простая команда
   не очищает outputs/cache и не вводит запрет сети или дополнительные рендеры.
   Существующие `.quarto/course-perf` и повторные измерения не попадают в нативные входы,
   опубликованный сайт или снимки экспериментов. Проверяются стандартные ресурсы,
   широкая маска `**`, другой каталог измерений внутри ресурсов, запрет записи,
   коллизии со служебным путём и output-dir. Пользовательский `.gitignore`
   сохраняет свои байты; служебные результаты не маскируют исходное Git-состояние.
   Отдельно проверяется однофайловый рендер с `--output-dir`, удаляющий scratch:
   текущий запуск сохраняется из временного каталога после завершения рендера,
   прежний запуск может исчезнуть при штатной очистке. Чужие данные Quarto
   не восстанавливаются. При ошибке сохранения текущие временные данные остаются
   доступны по напечатанному пути.
5. Ошибки Quarto, недоступный инструмент, конфликт диагностики, SIGINT/SIGTERM
   и невозможность записи отчёта дают различимые результаты и сохранённые
   сведения о фактическом завершении. Прерывания отдельно проверяются
   с Deno 2.7.14 и 2.9.7 на рендере с дочерним процессом: после возврата команды
   он не продолжает запись. Прежний падающий SIGTERM-тест воспроизводится
   перед исправлением и проходит после него.
6. `summary`/`cpu` сохраняют пользовательские TS/Lua и пакеты; отсутствие
   разметки/наблюдений отображается честно. `trace` доступен в изолированном
   эксперименте и не преобразует исходники простого рендера. Значимые результаты
   обычного Quarto и режимов `off`, `summary`, `cpu` сравниваются на представительном
   проекте, включая пользовательские runtime и Pandoc data-dir. Проверка не
   скрывает изменения содержимого общей нормализацией HTML.
   Отдельно проверяются публичная установка агентов без патча
   `run_emulated_filter`, эффективные `QUARTO_*`, пользовательский `init.lua`,
   достоверность `extension_id`/`document_id`, известные пробелы покрытия,
   отсутствие исполнителя и потеря действительно ожидаемого свидетельства
   запуска. Для совместимости старого/нового моста и агента ABI 1 достаточно
   узких отдельных примеров; вся интеграционная матрица на старых мостах
   не требуется.
7. Обобщённый эксперимент работает с другим именем репозитория и явной заменой
   пакетов. Сохраняются проверки SHA, хешей runtime, ограничений путей,
   повторных запусков и прежние проверки backend.
8. Рецепт действительно создаёт Arch-пакет. Проверяется состав и запуск из
   временно распакованного установленного дерева, затем в чистом окружении
   Arch, если оно доступно. Проверка системного pacman-install учитывается
   отдельно и не заявляется по результату одной распаковки.
9. Установленный инструмент работает из чужого каталога и с чистым cache,
   находит Lua/TS/registry, не пишет в `/usr` и не требует checkout Performance.
10. Перед выпуском проходят подходящие локальные проверки и CI на финальном
    исходнике. Выпуск включает инструкцию перехода и проверенный Arch-рецепт;
    исторические теги и Releases сохраняются.
11. Трассы импортируются в Perfetto с сохранением интервалов и подтверждённых
    связей. Асинхронные операции, разные часы, ошибки и неполные данные
    отображаются без вымышленной вложенности/синхронизации. Реальный CPU-профиль
    открывается в Speedscope; файлы доступны из отчёта после сохранения запуска
    в `.quarto/course-perf` или выбранном внешнем каталоге.
    Проверяются несовпадающие пары begin/end, дубликаты, неизвестный контекст,
    устаревший родитель дочерней команды, нормализованные пути Lua trace
    и отсутствие двойного счёта `delta`/`total`. Исходные повреждённые записи
    сохраняются; экспорт не исправляет их вымышленными интервалами.
12. Простой рендер и эксперимент используют общий построитель отчёта.
    Проверяются версии новых манифестов/сводок, неизменность сырой схемы 1,
    отдельный контракт производного экспорта и ссылки после переноса
    из временного каталога. Абсолютные исходные пути остаются достоверными.
