## Последние прямые решения пользователя

- Продукт работает с любыми Quarto-проектами пользователя на Course-Tools;
  имя Java, student/full и расположение каталога не зашиваются в общий путь.
- Основной вызов — `quarto-course-perf render`. Режим по умолчанию `off`,
  дополнительные простые режимы — `summary` и `cpu`; полный `trace` остаётся
  изолированным экспериментом. Собственные параметры имеют префикс `--perf-`.
- Отчёты — `.quarto/course-perf/runs/<run-id>`. Текущие данные собираются во
  внешнем staging и переносятся после остановки всего своего дерева процессов.
- Простой рендер сохраняет cwd/argv, функциональное окружение, cache/freeze,
  сеть и установленные пакеты. Он не обновляет расширения автоматически.
- Java разрешено и требуется перевести на новые согласованные полные пакеты
  перед основной приёмкой. Сохранить функции кандидатных правок и их происхождение;
  переносить необходимые изменения через владельцев, не патчить vendored файлы по одному.
- Cybersecurity не обновлять, не рендерить, не включать в обязательную матрицу,
  новый PR для него сейчас не создавать. Это уточнение заменяет прежний пункт
  общего `AGENTS.md` о финальном Cybersecurity PR.
- Perfetto — основной просмотрщик; Speedscope открывает существующий V8 profile.
  Первичные данные сохраняются. Не создавать вымышленные timestamps, документы,
  родительство или CPU/memory series из агрегатов.
- ABI 1 сохраняется с optional context; конфигурация и metadata v2 не меняют
  raw Event/executor-summary v1. README упрощается только в Performance.
- Выпуски инструментов, штатная документация в `gh-pages` и ограниченная
  очистка завершённых веток входят в финал; системная установка пакета и AUR — нет.

## Последовательность реализации

Подробные шаги и команды находятся в общем плане; эта таблица задаёт контрольные
результаты, которые контроллер не должен потерять при передаче между агентами.

| Задача | Результат | Обязательная проверка перед приёмкой |
| --- | --- | --- |
| 1 | Свежие исходники, сохраняемая история, типы metadata | SHA/версии/patch provenance; raw v1 и новые форматы различаются |
| 2 | Ленивый CLI render/experiment | Help/version без Java/config/сети; буквальный native argv и два `--` |
| 3 | Проект через inspect, эффективный runtime | Подпапка/nested/другая цель; `--to html` не путь; QUARTO overrides сохранены |
| 4 | Streaming, ресурсы и собственная process group | stdin/PTY/logs; SIGINT/SIGTERM; пишущий внук остановлен, сосед жив |
| 5 | Staging и общий построитель запуска | forceClean не теряет текущие raw; off-report; ссылки после переноса |
| 6 | Публичная установка summary/cpu | Без private Quarto patch; пользовательский data-dir/init.lua работает |
| 7 | Context, ожидания, качество и registry | Реальные document/extension IDs; нет ложной полноты; повреждённые пары исключены из totals/trace |
| 8 | Узкие owner-изменения и подготовленный Java | Новые полные пакеты; сохранены нужные candidate-функции; native student→full→student |
| 9 | Обобщённые эксперименты | Явный project source/replacements; сторонние пакеты сохранены; strict comparison |
| 10 | Perfetto/Speedscope | Реальный импорт/UI, раздельные часы, подтверждённые flows, CPU profile Java |
| 11 | Устанавливаемое дерево и Arch-рецепт | Реальный makepkg, offline assets, чужой cwd/deno.json, нет записи в `/usr` |
| 12 | Финальная Java-приёмка, README и выпуски | Проверки на финальных SHA, независимое review, releases/docs и защищённая очистка |

Не начинать заново принятые задачи после compaction. Сначала сверить журнал,
реальные Git commits, состояние рабочего дерева и незавершённый review/fix round.
Наличие галочки без подтверждающего commit и evidence недостаточно.

Для необходимых ранних выпусков зависимостей задача 8 делится на два gates:
8A — код/тесты каждого владельца, независимое review точного BASE..HEAD, затем
разрешённые controller merge/release; 8B — установка новых пакетов в Java,
native baseline, независимое review курса и OPEN PR. Это не разрешение worker
публиковать ещё не проверенный код. Финальный whole-branch review предшествует
выпуску Performance и публикации документации; изменение уже выпущенного owner
после него требует нового тега/выпуска и обновлённых Java pins/проверок.

## Технические доступы среды

Авторизация задачи не выдаёт технические права. Нужны запись в выбранные
checkout/worktree и их Git metadata, запуск локальных процессов, сетевой доступ
к нужным источникам, GitHub read и необходимые write/merge/release/ref операции
в перечисленных репозиториях. Использовать существующие connector, credential
helper или `gh`; не запрашивать токены текстом и не печатать секреты.

В текущей среде запись разрешена под `/home/tolya/course-tools` и `/tmp`;
network/sandbox restrictions могут требовать штатной эскалации конкретной
операции. Worktrees и caches предпочтительно размещать внутри разрешённых
каталогов, не менять глобальные настройки Codex или окружение пользователя.
Перед исполнением проверить фактические права новой сессии: приведённые пути
и наличие инструмента не доказывают наличие соответствующего разрешения.

У subagents действуют настройки sandbox/approval родительского запуска;
инструкция «read-only reviewer» задаёт роль, а не отдельную системную защиту.
Ни промпт, ни custom agent не могут ослабить эти ограничения.
[Официальная документация OpenAI](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls).
Режим без sandbox и безграничный `sudo` для этого плана не требуются.

Arch-проверку выполнять с готовыми зависимостями либо в изолированной Arch-среде.
`makepkg -s` разрешён внутри такой среды; на ноутбуке он способен вызвать pacman
и не является обходным способом разрешить host-установку зависимостей.
Команды `sudo pacman -Syu/-U/-R` в пользовательской инструкции — примеры,
не поручение исполнителю. Для host-изменения нужна отдельная конкретная просьба.

При отказе automatic approval review назвать операцию и причину; продолжать
независимую работу, при необходимости запросить ровно недостающий доступ.
Не обходить отказ другой оболочкой, другим агентом или записью вне sandbox.
Отсутствие доступа не объявлять успешной проверкой.

## Когда продолжать и когда обращаться к пользователю

В пределах явно разрешённого scope не спрашивать подтверждение каждой задачи,
обычного исправления, своего PR, предусмотренного выпуска или публикации.

действительно отсутствующее разрешение на конкретный выход за границы.

Новый серьёзный продуктовый конфликт показывать обычным текстом: наблюдаемый
пример, нарушаемое требование, варианты и рекомендуемое решение. Не открывать
заново принятые CLI/storage/Java/Cybersecurity решения. Независимые задачи
продолжать, зависимое действие без обязательного ответа не выполнять.
Границы разрешений не расширяются собственным решением контроллера.

Если пользователь отправит подготовленный стартовый промпт, бюджет исполнения —
9 часов от первого исполняемого действия этого запуска. Записать T0 и deadline
в журнале с UTC и Europe/Minsk; resume/compaction не создаёт новый бюджет.
При исчерпании сохранить состояние, commits/evidence и конкретный остаток;
не объявлять незавершённое завершённым. Подготовка этого handoff бюджет не запускает.

## Проверяемый финал

Установленный интерфейс, Java на новых полных пакетах, реальные Arch/Perfetto/
Speedscope проверки, русские инструкции и review должны относиться к итоговым
SHA. После merge повторно проверить изменившийся финальный исходник и выпускные
артефакты. Нельзя переносить успешный статус с другого кода или подготовительной ветки.

Передать ссылки на собственные PR, новые Releases/assets и опубликованную
документацию; оставить Java PR OPEN. В приложении прикрепить созданные PR к задаче
штатным инструментом, если он доступен. Зафиксировать сохранённые/удалённые ветки
и фактические ограничения, FAIL/INCONCLUSIVE/unavailable. Сохранить журнал и
исходные данные, достаточные для продолжения без истории чата.
