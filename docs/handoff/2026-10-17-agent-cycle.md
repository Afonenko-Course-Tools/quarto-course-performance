# Агентский цикл реализации quarto-course-perf

Этот документ задаёт работу будущего контроллера и не начинает реализацию.
Полномочия, границы выпуска и актуальные исходные данные задаёт
[основная передача](2026-10-17-general-use.md); вход в новый запуск —
[стартовый запрос](2026-10-17-start-prompt.md).
Долговечное состояние хранится в [журнале передачи](2026-10-17-progress.md).

## Единственный маршрут и восстановление

Единственная идентичность исполняемого плана:
`docs/superpowers/plans/2026-10-17-general-use-implementation.md`.
Контроллер читает [этот план](../superpowers/plans/2026-10-17-general-use-implementation.md)
и [спецификацию](../superpowers/specs/2026-10-17-general-use-design.md) целиком.
Приоритеты и новые серьёзные расхождения разрешаются по основной передаче;
план описывает способ выполнения, спецификация — требуемое поведение.

Задачи 1–12 выполняются по порядку: контракты → CLI → определение проекта →
процессы → хранение/отчёт → диагностика → контекст → владельцы/Java →
эксперименты → Perfetto → Arch → приёмка/выпуск. Не менять номера и границы этапов.
[План Perfetto](../superpowers/plans/2026-10-17-perfetto-visualization.md)
выполняется только внутри задачи 10, подшагами 10.1–10.4. Его собственные
номера 1–4 не становятся новыми задачами верхнего уровня или вторым запуском.
Для них не создавать отдельную идентичность плана или независимый журнал.

Перед любым назначением задачи и после сжатия контекста/смены сессии:

1. Проверить текущие worktrees, ветки, HEAD и незакоммиченные изменения;
   не считать прежний путь гарантией прежнего содержимого.
2. Прочитать журнал передачи, рабочий журнал именно этого плана и указанные
   свидетельства; сверить SHA с Git. История чужого плана не подтверждает завершение.
3. Найти первый незавершённый этап либо незакрытый раунд исправлений. Строка
   `Task N: complete` с проверяемыми коммитами/ревью означает пропуск назначения,
   а не повтор работы «для уверенности». Не создавать замену живому исполнителю.
4. Если временные материалы отсутствуют, восстановить их по сохранённым сводкам,
   refs и свидетельствам; их отсутствие не означает, что все задачи снова pending.
5. Проверить записанные T0/deadline: девять часов отсчитываются от первого
   исполняемого действия нового запуска; возобновление не обнуляет отсчёт.

## Настройка контроллера

Прочитать актуальный `superpowers:subagent-driven-development` целиком, включая
шаблоны запросов. Найти абсолютный каталог навыка через доступный каталог
skills текущей среды; записать его как `SKILL_DIR`. Не переносить путь cache
с прежнего ноутбука/версии. Выполнять скрипты через `bash` и абсолютный путь:

```sh
PLAN=docs/superpowers/plans/2026-10-17-general-use-implementation.md
bash "$SKILL_DIR/scripts/sdd-workspace" "$PLAN"
bash "$SKILL_DIR/scripts/task-brief" "$PLAN" "$N"
bash "$SKILL_DIR/scripts/review-package" "$PLAN" "$BASE" "$HEAD"
```

Рабочий каталог этих команд — выбранная рабочая копия Performance. Сохранить
фактический путь workspace, напечатанный скриптом, и прочитать его `plan-path`.
Первая строка `<workspace>/progress.md` должна быть:
`# SDD ledger — plan: docs/superpowers/plans/2026-10-17-general-use-implementation.md`.
Рабочие каталоги других планов и старый плоский журнал не изменять.

На момент передачи `task-brief` распознаёт только заголовки `Task N`, тогда
как текущие планы используют `## Задача N —`. Проверить установленную версию:
пустое задание/код 3 не являются успехом. При этой несовместимости извлечь точный
раздел от нужного `## Задача N —` до следующего `##` в файл того же workspace;
сверить начало, конец и полноту с оригиналом. Не пересказывать требования и
не переименовывать план ради скрипта. Для задачи 10 приложить точные тексты
подшагов Perfetto к её заданию, сохранив единственную основную идентичность плана.

Сначала сохранить таблицу предварительной проверки: строка для каждой задачи
о внутренней согласованности и строка для каждой пары с общим файлом/интерфейсом:
производитель → потребитель, зависимость, конфликт, решение. Проверить особенно
общие типы, normalize/report, ABI владельцев, входы Java и происхождение выпуска.
Решения записывать как `Ruling: решение — основание — цена ошибки`.
Оговорка плана не освобождает требование от независимого ревью.

## Роли, ресурсы и границы записи

- Бюджет — четыре одновременных агента вместе с контроллером. Обычный цикл:
  контроллер + один исполнитель, затем контроллер + свежий рецензент.
- Новый исполнитель на каждую задачу; назначение с `fork_turns: "none"` передаёт
  узкое задание и нужные интерфейсы без истории сессии. Рецензент тоже получает
  свежий контекст. Исполнитель и рецензент сами агентов не создают.
- В одном общем worktree одновременно только один пишущий исполнитель.
  Контроллер не исправляет код вместо него; рецензенты работают только на чтение.
- По умолчанию один исполнитель. Явно разрешённые планом/передачей независимые
  работы владельцев задачи 8 допустимы лишь в отдельных worktrees с непересекающимися
  файлами после закрепления ABI; интеграция общих файлов последовательная.
  Само наличие свободного слота не разрешает параллельную запись.
- Реализация и тесты — `medium`; спецификации, README, docs, инструкции,
  шаблон и Java-проекты — `ultra`, если выбранная среда поддерживает настройку.
  Выбирать только реально доступные модели/уровни рассуждения; записывать выбор.
  Если настройка недоступна, сообщить ограничение, не утверждать её применение.
- Использовать внутренних агентов текущего запуска. Новые пользовательские
  чаты и сообщения в существующие чаты требуют отдельного разрешения человека.

Не спрашивать между уже разрешёнными шагами, коммитами и проверками.
Технические разрешения sandbox обязательны; отказ нельзя обходить сменой механизма.
При новом серьёзном продуктовом расхождении показать конкретный пример и варианты
обычным текстом, продолжая независимые разрешённые работы; не открывать заново
уже согласованные вопросы. Детали полномочий внешних действий — в основной передаче.

## Назначение задачи и отчёт исполнителя

Перед назначением закрепить полный BASE командой `git rev-parse HEAD` именно
в рабочем дереве владельца, ветку, разрешённые файлы и результаты зависимостей.
Записать ID агента. Задание — отдельный файл с полным текстом задачи, относящимися
к ней точными ограничениями и решениями контроллера. Все пути задания, отчёта,
входных данных и worktree в сообщении должны быть абсолютными и проверенными.

```text
Задача: N, название; место в общем маршруте: …
Работай в: <абсолютный worktree>; ветка: …; BASE: <полный SHA>.
Сначала прочитай требования: <абсолютный путь задания>.
Входы: <разделы spec, refs владельцев, данные, нужные интерфейсы с путями>.
Разрешённые файлы/ожидаемые результаты: <точный список>.
Решения и зависимости: <только относящиеся к этой задаче>.
Выполни требуемые проверки; коммить только собственные изменения.
Сам проверь diff. Не создавай агентов/рецензентов и не меняй чужие файлы.
Полный отчёт запиши в <абсолютный путь отчёта>; верни короткий статус и SHA.
```

Исполнитель сохраняет фактические команды, версии, cwd, код завершения, значимый
вывод и пути свидетельств; где план требует RED/GREEN — обе реальные стадии.
Не заменять результаты фразой «должно проходить». Отчёт привязан к проверенному
HEAD; позднейшие правки не наследуют автоматически прежний успех тестов.

```text
Статус: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
Задача / worktree / BASE / HEAD / коммиты: …
Реализовано и изменённые файлы: …
Проверки: команда; cwd/runtime; exit; результат; путь к полному свидетельству.
RED/GREEN, если требовались: …
Самопроверка, ограничения/проблемы и незавершённые требования: …
Путь полного отчёта: …
```

`DONE` направляется на ревью. У `DONE_WITH_CONCERNS` сначала разобрать риски
корректности/границ задачи. `NEEDS_CONTEXT` получает недостающий контекст;
`BLOCKED` — изменённый подход, размер задачи или доступную более сильную роль.
Не игнорировать эскалацию и не отправлять прежний пустой запрос на повтор.

Задача 8 имеет две зависимые части. В 8A каждый владелец проходит собственные
код/проверки → независимое ревью его `BASE..HEAD` → проверку выпуска контроллером →
новые неизменяемые теги/полные пакеты. Исполнитель не публикует до этого ревью.
Такие предварительные выпуски нужны для 8B: штатное обновление Java, обычный
рендер до измерений, отдельное ревью Java и OPEN PR. Общая задача 8 завершена
после обеих частей. Если позднее меняется код владельца — новый выпуск,
обновлённые Java refs и затронутые проверки; прежний тег не переназначать.

## Независимая проверка задачи

Зафиксировать полный HEAD после исполнителя и сформировать пакет ревью скриптом
по диапазону `BASE..HEAD` с исходным BASE задачи; никогда не использовать `HEAD~1`.
Пакет должен содержать коммиты, stat и полный diff с контекстом, включая все
коммиты задачи. Для каждого владельца — свой диапазон и отдельный пакет.
Сохранить фактический путь пакета из вывода команды и проверить его наличие.

Свежему независимому рецензенту передать те же задание/отчёт, пакет и точные
применимые ограничения спецификации. Отчёт исполнителя — утверждения для сверки,
не доказательство корректности кода. Рецензент читает diff и только по названному
конкретному риску проверяет узкое внешнее место. Два обязательных вердикта:

```text
Прочитай <задание>, <отчёт>, <пакет ревью BASE..HEAD>.
Проверь соответствие требованиям и качество независимо; только чтение.
Ограничения этой задачи из spec: <точные применимые пункты>.
Spec compliance: PASS | FAIL; пропуски/лишнее/ошибки с file:line.
Cannot verify from diff: <что должен проверить контроллер>.
Task quality: APPROVED | NEEDS_FIXES.
Находки: Critical / Important / Minor; file:line, риск и основание.
Проверенные места и использованные свидетельства: …
```

Не требовать благоприятного вердикта, не запрещать конкретные находки и
не понижать серьёзность заранее. Самопроверка не заменяет независимый этап.
Не дублировать уже выполненные проверки на том же коде: использовать свидетельства.
Новая узкая проверка допустима для конкретного сомнения без ответа в них;
широкую дополнительную проверку сначала обосновать контроллеру.
Отсутствующее/обрезанное свидетельство сначала перечитать по пути, а не пересоздавать
повторным набором проверок. Контроллер закрывает каждый `Cannot verify from diff`.

## Исправления и завершение задачи

Spec FAIL, Critical/Important и подтверждённый пробел запускают цикл исправлений.
Minor записать с основанием отсрочки для финального ревью. Конфликт находки
с планом разобрать по spec и записать Ruling; не отбрасывать его молча.
Один раунд = назначение исправления + ревью его границ; максимум пять на задачу.

1. Раунды 1–3: вернуть исходному исполнителю дословные открытые находки, пути
   задания/отчёта и конкретные покрывающие проверки. Если агент недоступен — свежий
   исполнитель восстанавливает работу по этим файлам.
2. Раунды 4–5: свежий исполнитель и доступная более сильная модель в пределах
   заданных правил medium/ultra; указать прежние попытки и отчёт. Недоступную эскалацию
   не выдумывать: записать ограничение и использовать свежий контекст.
3. Исполнитель дописывает тот же отчёт: изменения, команды и результаты проверок,
   покрывающих изменённый код. Не отправлять повторное ревью без этих свидетельств.
4. Пакет строится по `FIX_BASE..HEAD`, где FIX_BASE — head прошлого ревью.
   Рецензент отвечает ADDRESSED/NOT_ADDRESSED по каждой находке и отмечает новое
   повреждение только в diff исправлений. Остальное — отложенные Minor.
5. Записать раунд, коммиты, ID рецензента, закрытые/открытые находки в оба журнала.
   После пятого раунда не продолжать бесконечные назначения: разобрать остатки.

Спорное или реально несущественное можно отложить только с явным Ruling и ценой
ошибки; структурный дефект нельзя объявлять успешно исправленным. Если он
затрагивает следующий шаг, закрепить необходимое исправление и его проверку;
при новой серьёзной неопределённости действовать по основной передаче.
Завершать этап лишь с обоими положительными вердиктами либо явно записанными
после предела решениями; релизная приёмка всё равно требует выполнения spec.
Оставшийся реальный обязательный критерий не превращать в принятый Minor:
закрепить необходимое исправление/его владельца, сохранить незавершённый статус
критерия и выполнить его перед приёмкой зависимой работы и выпуском.
Запись: `Task N: complete (commits <BASE>..<HEAD>, review clean | K parked)`.
Для задачи 10 эта строка появляется только после всех подшагов 10.1–10.4.

## Финальное ревью, выпуск и сохранение истории

После реализации задач 1–11 и изменений задачи 12, до выпуска Performance и
документации, — свежий рецензент всей ветки наиболее сильной доступной роли.
Передать пакет от записанного branch base/MERGE_BASE до финального HEAD,
spec, отложенные находки/Ruling, матрицу SHA владельцев/Java и свидетельства;
изменения разных репозиториев представить отдельными диапазонами.
Ранние выпуски владельцев 8A уже прошли свои проверки; повторно их не выполнять.
При находках — один общий исполнитель исправлений и одно ревью их границ;
остатки явно разобрать, не объявляя незакрытую обязательную приёмку успехом.

Задача 8 должна подготовить обновлённый Java до основной приёмки задач 9–12.
Cybersecurity сохраняется и отложен; его рендеры/обновление/новый PR не добавлять.
На финальном source SHA выполнить предусмотренные локальные/CI, Java, viewer и
installed checks. Выпуск 2.0.0, исходный архив/hash, Arch-пакет, выпуски владельцев
и опубликованные docs должны ссылаться на проверенные версии. Если подготовка
выпуска изменила code/assets/dependencies/входы пакета или source SHA,
обновить сведения о происхождении и повторить затронутые проверки; прежнее ревью
не покрывает новый код автоматически. Проверить опубликованные артефакты и ссылки.

После каждого этапа/исправления/Ruling синхронизировать отслеживаемый Git журнал:
статус, BASE/HEAD, refs, пути отчётов/ревью/свидетельств, фактические проверки,
остатки и следующий шаг. Временный журнал удобен в сессии, но исключён из Git:
он один не переживёт новую рабочую копию. Перед передачей или очисткой сохранить
нужные свидетельства аудита и отчёты в долговечные артефакты/refs с проверяемыми
hashes; журнал должен позволять найти их без памяти чата.
Не удалять единственную копию журнала/workspace, пока архив и восстановление
не проверены. Не применять `git clean -fdx` как подготовку или финальную уборку.
Очистка веток и worktrees выполняется только по основной передаче после
сохранения истории; пользовательские course worktrees, serving gh-pages,
main, OPEN PR refs, теги/Releases сохраняются. В итоговой передаче перечислить
все Ruling по порядку с ценой ошибки, фактические проверки и честные ограничения.
