# Стартовый промпт для реализации quarto-course-perf

Текст ниже предназначен для отправки пользователем в новую сессию Codex.
Его чтение как файла или цитаты не является отдельным разрешением начать работу.

---

Реализуй согласованный план quarto-course-perf до проверенного выпуска.
Это поручение на исполнение, а не повторное планирование. Рабочий корень:
`/home/tolya/course-tools`; основной репозиторий:
`/home/tolya/course-tools/quarto-course-performance`.

Сначала прочитай `START-CODEX.md`, применимые `AGENTS.md`, затем файлы основного
репозитория:

1. `docs/handoff/2026-10-17-general-use.md`.
2. `docs/superpowers/specs/2026-10-17-general-use-design.md`.
3. `docs/superpowers/plans/2026-10-17-general-use-implementation.md`.
4. `docs/superpowers/plans/2026-10-17-perfetto-visualization.md`.
5. `docs/handoff/2026-10-17-agent-cycle.md` и `2026-10-17-progress.md` рядом с ним.

Основной интерфейс — установленная команда `quarto-course-perf render`,
результаты — `.quarto/course-perf`. Нативное поведение Quarto сохраняется;
простое измерение не обновляет пакеты. Перед основной приёмкой отдельно
переведи Java на новые согласованные полные версии расширений и мостов,
сохранив нужную функциональность кандидатных правок. Зафиксируй новые Java SHA,
versions/hashes и происхождение пакетов. Cybersecurity отложен: не обновляй,
не рендери, не включай в тестовую матрицу и не создавай для него новый PR.
Это последнее уточнение заменяет старое требование общего AGENTS о Cybersecurity.

Сверь актуальные GitHub heads/контракты, сохрани все пользовательские изменения
и создай изолированные worktrees в существующих репозиториях. Не создавай Git
в корне course-tools. Сохрани handoff и локальные плановые commits при выборе
свежей продуктовой основы. Дальше выполняй все 12 задач без остановок между ними.

Используй агентский цикл: контроллер → свежий исполнитель → независимый
task review требований и качества → исправления и узкое повторное review →
запись принятого этапа. В финале — независимое review всей реализации.
Разрешаю subagents; новые пользовательские чаты не создавай. Не допускай двух
писателей в одни файлы. Реализация/тесты — medium; спецификации, README, docs,
инструкции и работа с Java — ultra, если среда поддерживает настройку. При
отсутствии нужного уровня используй доступный и честно зафиксируй это.

Разрешаю в пределах handoff:

- изменения кода, контрактов, тестов и документации затронутых владельцев;
  локальные сборки/рендеры, worktrees, branches и commits;
- сеть для GitHub/официальных источников, fetch/clone, закреплённых зависимостей
  и инструментов проверок; имеющуюся GitHub-аутентификацию без раскрытия секретов;
- push своих веток, создание/обновление собственных PR и технические ответы
  в них; merge собственных PR инструментов/шаблона этой реализации после
  обязательных проверок и независимого review, без обхода защит;
- новые теги/Releases затронутых инструментов и проверенные assets,
  Performance2.0.0, штатную публикацию документации в существующую `gh-pages`;
- подготовку обновлённого Java и передачу отдельным OPEN PR; Java PR не сливать
  и не закрывать, исходные ветки/PR/head и рабочие деревья сохранять;
- сборку и проверку Arch-пакета в готовой/изолированной среде;
- удаление завершённых LOCAL/REMOTE веток только инструментов/шаблона после
  сохранения истории и проверки списка кандидатов. Сохраняй main/default,
  serving gh-pages, heads OPEN автоматических PR, все tags/Releases и course
  ветки/worktrees. Не затрагивай активную работу других сессий.

Не разрешаю host-установку/удаление системных пакетов или самого Performance,
AUR, выбор выдуманной лицензии, переписывание старых release assets/тегов,
публикацию сайта курса, закрытых данных или изменения посторонних проектов.
`makepkg -s` с установкой зависимостей выполняй в изолированной Arch-среде;
на ноутбуке собирай с уже доступными зависимостями. Для host-изменения сначала
подготовь конкретное действие и запроси отдельное разрешение.

Эти разрешения не отменяют sandbox, automatic approval review и GitHub branch
protection. Недостающий технический доступ запрашивай штатно только для нужной
операции; при отказе назови действие/причину и продолжай независимую работу.
Не спрашивай повторное подтверждение уже разрешённых этапов, PR, выпусков
или публикации. Новый серьёзный конфликт показывай с конкретным примером и
вариантами; согласованные решения заново не открывай.

На этот запуск исполнения даю 9 часов от первого исполняемого действия.
Запиши T0/deadline в UTC и Europe/Minsk в журнал; после resume не обнуляй бюджет.
Проверяй локально, CI используй на финальных этапах. Не выдавай наличие файла
или старый pilot evidence за пройденный тест. Сохраняй commits, receipts,
review/fix rounds и следующий шаг после каждого этапа для восстановления без чата.

Начинай с проверки состояния и первой незавершённой задачи. В финале передай
результаты Java/Arch/Perfetto, ссылки на PR/Releases/документацию, точные SHA
и оставшиеся ограничения. Если время или обязательный доступ исчерпаны,
сохрани состояние и конкретный остаток, не объявляй незавершённое завершённым.
